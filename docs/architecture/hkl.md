# HKL Core — Architecture Reference

Architecture source of truth for the HKL viewer app (`apps/hkl/`). **For how to *use* HKL — controls, tunings, playing, recording — see the [Core guide](../guide/core.md).** For the project overview, tuning theory, and coordinate system see [`../architecture.md`](../architecture.md); for sample playback internals see [`engine.md`](engine.md) (the `@hkl/engine` package).

## Hardware integration

### Lumatone

- **Layout**: 5 boards × 56 keys = 280 keys, hexagonal isomorphic.
- **Physical board swap** (some units, incl. Max's): boards 3 and 4 are physically transposed. Handled by a persisted, off-by-default toggle (*Calibrate Keys → "Swap boards 3 ↔ 4"*, pref `swapBoards34`). All SysEx board-byte routing goes through `sysexBoardFor(group)` (`lumatone/protocol.ts`): identity `[1,2,3,4,5]` when off, `[1,2,3,5,4]` when on. Only the board byte flips — `fixedMidiChannelMap` is group-keyed and unaffected. Flipping the toggle re-pushes the fixed layout + colors so the relocated boards re-light.
- **Connectivity**: USB-MIDI (primary), 5-pin DIN in/thru/out, 1/4" Sustain jack, 1/4" Expression jack.
- **SysEx envelope**: `F0 00 21 50 <board> <cmd> <data1-4> F7`. Manufacturer ID `[0x00, 0x21, 0x50]`. Per-key data: (keyIndex, noteNum, channel-byte 0-indexed, typeByte) where `typeByte = (faderUpIsNull << 4) | keyType`, keyType ∈ {0=disabled, 1=noteOnNoteOff, 2=CC, 3=lumaTouch}. `lumaTouch` is a continuous fader, NOT poly aftertouch.
- **Commands HKL uses**: `0x00 CHANGE_KEY_NOTE` (note/channel/keyType per key), `0x01 SET_KEY_COLOUR` (8-bit RGB as 6 nibbles), `0x07 SET_LIGHT_ON_KEYSTROKES`, `0x0E SET_AFTERTOUCH_FLAG` (global poly aftertouch), `0x0F CALIBRATE_AFTERTOUCH` / `0x24 CALIBRATE_KEYS` / `0x52 CONFIRM_CALIBRATION` (the built-in touch calibration; Lumatone internals → Built-in calibration), `0x31 GET_FIRMWARE_REVISION`, `0x33 LUMA_PING` (liveness heartbeat), `0x38 CALIBRATE_EXPRESSION_PEDAL`, `0x39 RESET_EXPRESSION_PEDAL_BOUNDS`, `0x3E PERIPHERAL_CALIBRATION_DATA`. The authoritative command list for the installed firmware is its own `sysex*` enum (readable from the binary's debug info; 1.5.0 adds `0x52`–`0x55`, below); the Terpstra editor source, https://github.com/hsstraub/TerpstraSysEx.2014, documents the established set.
- **LED throughput depends on board ordering**: a standalone USB-MIDI benchmark measured ~121 changed-key updates/s on one board vs ~318/s interleaved (alternating two boards gives the full gain), so color sync sweeps the boards interleaved, top to bottom. ~100/s is not a global LED ceiling. Measured on firmware 1.4.0 (2026-09-22); 1.5.0 changed the BBB→PIC write path and adds batched `0x55` color frames, and neither has been measured or used yet. Details: [`tools/lumatone-bench/README.md`](../../tools/lumatone-bench/README.md); gate `test/hkl-midi/sync-order.mjs`.

### Pedal jacks

| Jack | CC | Behavior |
|---|---|---|
| Sustain | 64 (binary) | Switch pedals work; continuous half-damper quantized to binary by firmware. |
| Expression | 4 (Foot Controller) | Roland-wired (wiper on ring). Continuous. |

- **Expression wiring**: Roland convention (T=end1, R=wiper, S=end2). Works: Roland DP-10 (Continuous mode), Roland EV-5, Yamaha FC7 (with firmware Invert toggle). **Does NOT work**: Korg-convention pedals (DS-1H, DS-2H — ring floating, ADC reads noise indistinguishable from a binary switch).
- **Calibration mode** (CMD 0x38): learns ADC bounds for the connected pedal. While active, firmware emits CMD 0x3E status packets every ~100ms with running min/max + valid flag.
- CC numbers are **not** remappable via SysEx. Sensitivity (CMD 0x03) is a 0–127 gain scalar; polarity invert (CMD 0x04) is boolean.

### Lumatone internals (reverse-engineered)

Needed for per-key hardware calibration (the only way to set key thresholds and velocity values numerically rather than by touch) and for diagnostics. Normal HKL operation requires none of it. → full workflow in [`../lumatone-calibration.md`](../lumatone-calibration.md). The same **Calibrate Keys** overlay (`lumatone/lumadiag.ts`) hosts, at its top, the built-in calibration (Start key calibration / Start aftertouch calibration, replaced by Confirm / Cancel while one runs; below), and the velocity-calibration UI — per-board threshold/sensitivity sliders with Get / Reset (plus Get all values / Reset all 5 boards and per-board velocity, AT and Lumatouch LUT resets), Push identity LUT (CMD 0x08) and the firmware interval-curve sliders + push (CMD 0x20), both of which also go out with every setup (Lumatone output → Velocity tables), the Lumatone velocity curve (its graph against input velocity and its two sliders, **full at** and **gamma**: engine.md → Velocity architecture), per-key velocity statistics and the per-key press-time scale (**Import key scales…** for the table `keydata-compare.py --scales` writes, the capture pass, Clear; engine.md → Velocity architecture) — and, since 2026-09-13, the **Layer loudness match** slider: `prefs.layerBlend` → `SampleEngine.setLayerBlend`, the log-linear blend between a re-gained `.hki`'s level-matched (`gainLevel`) and sones-matched (`gain`) layer gains (see engine.md "Layer-blend gain").

- **Hardware**: BeagleBone Black running Debian + 5 PIC microcontrollers (one per board). BBB↔PIC over UART `/dev/ttyO1`; host↔BBB over USB-MIDI. BBB is also a USB-ethernet gadget — device IP `192.168.6.2` (Linux host) / `192.168.7.2` (Mac/Windows). SSH `debian`/`temppwd`. Firmware: `/home/debian/LumatoneController/LumatoneController` from 1.5.0 on (static, non-PIE; `TerpstraController/` is a symlink to the new folder), `/home/debian/TerpstraController/TerpstraController` through 1.4.x (PIE) — ARM 32-bit ELF with debug info, respawned forever by `lmtn_launcher.sh`.
- **Firmware 1.5.0 protocol additions** (enum-diffed against 1.4.0; every existing code unchanged): `0x52` ConfirmCalibration (ends a key or aftertouch calibration from software, via the new PIC command `0x6a`: board `0` = all boards or 1–5, value `1` = confirm, `0` = cancel; NACK when no calibration is running); `0x53`/`0x54` Set/Get ProgramChange (mode bit 0: a preset button also sends a PC; bit 1: an incoming PC on the configured channel switches preset; default 0, and a send-mode press still switches the on-device preset); `0x55` SetOctaveColours (batched color frames: board `0` + 840 data bytes, or board 1–5 + 168, length checked exactly; 56 keys × 7-bit R, G, B per board, stored `<< 1`; the ACK is deferred until every responding board's PIC has the colors, and a frame sent before it replaces the pending one and swallows its ACK, so keep one in flight; details in `tools/lumatone-bench/README.md`).
- **Board liveness (1.5.0)**: the BBB marks an octave board not-responding when its data line stays high > 50 ms after CTS ("RTS stuck high"), or when it has PIC commands pending and nothing has been heard from it for > 3 s ("no reply to messages"; suppressed in calibration modes). Marking answers the host's in-flight `0x00`/`0x01` with code 3 (ERROR) and drops that board's pending PIC commands. Until any message from the PIC revives it ("octave N recovered"), SysEx addressed to it is answered ERROR and it is re-probed every 5 s. An idle board with nothing pending is never marked, so a GET such as `0x3A` (answered from BBB memory) is not a liveness test. Through 1.4.x there was no such state, and the BBB's wait on a PIC's data line had no timeout. `sysex.ts` moves on from any non-BUSY answer.
- **Built-in calibration** (`lumatone/keycal.ts`; the top section of Calibrate Keys): the firmware's own touch-learning routine, started with `0x24` (keys) or `0x0F` (aftertouch) — 11 bytes, board byte 0 — and ended with `0x52`. HKL sends a start only to firmware 1.5.0+: older firmware ends the routine only on a board's two macro buttons. While it runs the firmware answers **every command except `0x52` with STATE (4)**, so the phase (`lumatone.keyCal`: `idle` · `starting` · `key` · `aftertouch` · `unknown` · `ending`, written only by keycal.ts) holds `syncLumatoneColors` off; the heartbeat needs nothing, since a STATE reply is still an inbound message. After `0x52` is ACKed the mode returns to normal only once every board has reported back, so keycal.ts polls `0x31` every 300 ms (20 tries) until the answer is not STATE, then voids `deviceColors` and re-syncs (the routine repaints the keys) and the overlay re-reads the per-board values. A board that never reports back (one in the key diagnostic display, which only its own two macro buttons leave) returns the phase to running with Confirm / Cancel still offered. The device's answers drive the phase: STATE to a start, or to the connect-time firmware query (`queryFirmware`'s `onRefused` → `adoptKeyCal`: a page reloaded mid-calibration), gives `unknown` and offers the way out; NACK to `0x52` means it was not calibrating; STATE to `0x52` means another mode (pedal calibration, demo), and HKL lets go. Confirm rewrites `KeyData_N` (MAX, MIN, AT-MAX rows); Cancel writes nothing. Each board's own macro buttons keep working inside the PIC while the routine runs: releasing one confirms that board alone, the other cancels it, and the board leaves the routine early; the diagnostic display opens only when a button is held down while a key registers. What the routine and the diagnostic display do inside the PIC: lessons.md → "The PIC's calibration mode". Gate: `test/hkl-midi/keycal.mjs`. Saving and restoring the files: `tools/lumatone-cal/keydata-backup.sh`.
- **Baseline**: firmware facts in this doc and lessons.md were established on 1.4.0. 1.5.0 kept every command code, the per-board memory layout and the `files/` formats; what it changed is listed here and noted in place.
- **Per-key calibration state** lives in two layers:
  - **Disk** (persistent): `/home/debian/LumatoneController/files/KeyData_1..5` (`TerpstraController/files/` before 1.5.0), plain text, 4 sections × 56 values (MAX/MIN/validity/AT-MAX thresholds). Loaded when the controller starts, pushed to PICs.
  - **RAM** (volatile): `boardId[5]` in `.bss`, one 638-byte `board_properties` per board (`channel[56]` at 0, `note[56]` at 56, then colors); offsets `+0x118` MAX, `+0x150` MIN, `+0x1c0` validity, `+0x1fe` AT-MAX. Same layout in 1.4.0 and 1.5.0; only its address differs. Lost at restart/power cycle. (Older notes call this `kbd_preset_params`, which is really a 5-byte keyboard-flags struct.)
- **Indexing**: both layers use **PIC number** (`sysex_board`), not spatial board position. Slot `i` ↔ `KeyData_(i+1)` ↔ PIC `i+1`. The `sysexBoardFor` physical-swap only enters when translating spatial board_group → PIC number, never when indexing firmware structures.
- **Per-board thresholds** (`files/ThresholdData_1..5`, the sliders in Calibrate Keys; the firmware saves a slider change itself and HKL keeps no copy): `max` and `min lo` are how many counts of every key's swing are left out of its timing window, at the top and at the bottom. Stock is `max` 8, `min hi` 15, `min lo` 3. Max's unit ran `max` 15 and `min lo` 14 from May to November 2026 without a record, which shortened every window by 18 counts; since 2026-11-22 it holds `max` 15, `min lo` 3. What each does, why `max` stays, and the rule to write such changes down: lumatone-calibration.md → "The per-board thresholds set every key's timing window"; lessons.md → the `ThresholdData_N` entry.
- Tooling: `tools/lumatone-cal/` works on the disk layer from the host: `keydata-backup.sh` saves, verifies, checks and restores `KeyData_N` / `ThresholdData_N` over SSH, and `keydata-locate.py` names a key's file and slot, so a threshold is set by number by editing a saved file and restoring it (loaded at the next power cycle). `keydata-compare.py` compares saved folders from repeated runs of the built-in calibration (per-key repeatability, timing windows, each key against the same slot on the other boards) and writes their per-key median. The scripts that wrote the RAM layer through `/proc/<pid>/mem` were tied to 1.4.0's binary and were retired on 2026-11-11 (lumatone-calibration.md; decisions.md).
- **Local firmware mirror**: a host copy of the device's `debian` home (the controller binary, `LMTN-01_OctaveBoard.hex` for the PICs, `files/`) means analysis needs no device; refresh it after a firmware update, or it disassembles the previous version. Disassemble with `gdb -batch -ex "disassemble <fn>"`: host binutils builds usually lack an ARM target, so `objdump -d` fails.
- **PIC→BBB frames** are terminator-framed with no checksum or length field, and carry key travel time rather than velocity (the BBB rebuilds velocity via `files/VelocityLookUp_N`) — full detail in lessons.md.

### Self-contained audio

The Lumatone sends MIDI on a fixed (channel, note) scheme. HKL maps those addresses to lattice positions, computes frequencies from the active tuning system, and renders audio through `@hkl/engine` — no external synth in the path. A3 = 220 Hz is the central reference.

## Features

### Display

- **Hex grid** rotated counterclockwise; `tiltAngle` is set by `setRotation(mode, mapping, pose)` in `apps/hkl/src/layout/geometry.ts`. Vertical Freq (average pitch gradient vertical) and Piano (q-axis horizontal) are properties of the lattice and ignore the pose; Lumatone levels the case row (the (+7, −2) board step) of the visible outline in its pose — `outlinePose` in `layout/physical.ts`: the alignment for the Lumatone / QWERTY outlines, vertical for Piano / None — computed from that vector's pixel direction, so under Left / Right the lattice turns and the outline holds still. Gradient: q-axis = log(2)/3 per step (octave constraint); r-axis = midpoint of 5-limit log(3/2) and 7-limit adjusted value.
- **Canvas sizing**: width = max(400, viewport − 24px − a classic scrollbar while the lattice scrolls); height from the outline's vertical extent + `padY = hexR + dxH × 0.5`, symmetric about the canvas middle (`kbOffY = 0`). The Piano and None outlines take the piano footprint's height over every ref, computed at runtime (docs/architecture.md → Piano canvas height), so a ref change never resizes the canvas. `.wrap` `min-width: 424px`.
- **Scroll box** (`#cvScroll`, `index.html`): the canvas sits in a box that is its own height while it fits; otherwise the page's flex column caps it at the space the open toolbars and the analysis row's `min-height: 180px` (room for a staff — staff inset or Composer view) leave, and it scrolls vertically: wheel, scrollbar or keys, never touch (`touch-action: none`, so taps stay key presses). `applyCanvasHeight` (`render/controls-core.ts`) sets the height everywhere it changes and then centers the scroll on the canvas middle (the outline center / kbAnchor, or the piano view center); an unchanged height keeps the user's scroll. `refitCanvasWidth` re-derives the width on window resizes and, through a `ResizeObserver` on the box, when toolbars open or close. Hit-testing reads `cv.getBoundingClientRect()`, so it is scroll-safe. The OBS overlay keeps the whole canvas (`html.overlay #cvScroll` doesn't scroll or shrink; no reserved analysis row).
- Hex shapes drawn in rotated context; note text drawn unrotated for readability.
- **Extend pattern toggle** clamps cell range to keyboard extent when off. Disabled (forced on) while Outline is None, which has no extent to clamp to (`ui/controls.ts`).

### Controls

A **tabbed toolbar** (`apps/hkl/src/ui/toolbars.ts`): a selector row (`Layout · Playback · Analysis · Recording · Lumatone · Piano`, plus a `Reset` prefs button) toggles its own fixed-height `.toolbar-group`, any number open at once — tabs just flip `.tb-hidden`. Layout and Playback start open; the open set persists as `prefs.toolbars`. A seventh tab, `Secrets`, works the same way but is itself hidden until a hidden game has been discovered (Internal subsystems → Hidden games). Within a group, controls are stacked vertically wherever they fit, to keep the row narrow:

- **Layout**: two columns of stacked selectors — Tuning + Mapping + Hex size, and Outline + Rotation + Alignment (paired selects made equal-width via `.lsel-col`) — flanking the Note names / Banded layout / Show bands / Extend pattern checkbox column. **Banded layout** (`setBanded`, `ui/controls.ts`; pref `banded`) switches the unbanded layout (architecture.md → Unbanded layout) as a tuning change: the lattice stays static — every cell keeps its (q, r), held voices ramp in place — and only pitch, spelling, color and HEJI change. The keyboard anchor is the ref itself in both layouts (`state/reference.ts`), so a toggle never moves the Lumatone/QWERTY map; the ref is re-validated against the layout's own valid-ref set. `syncBandedControls` disables Show bands (no seams are drawn) and, unbanded, the P8 transpose where the frame has no spelled octave (`octaveVector`: Euler) and SC everywhere. The piano canvas height is computed per banding (docs/architecture.md → Piano canvas height); the picker ranks Schismatic under banded Semiditonal in both layouts, and chord analysis drops its V→D substitution and schismatic flag unbanded (the seam is the PM3 it sounds). Banding rides `.hkr` (`applySnapshot` restores it), `tuning-changed` / `hkl-layout-state`, the overlay snapshot and the piano-outline cache key.
- **Playback**: the instrument/waveform selector, with the Audio + Diagnostics checkboxes and the Import button beneath it (`.pb-stack`) · Transpose · Clear. **Diagnostics** (needs Audio) is the dev overlay for vetting sustained instruments (`audio/diagnostics/loopOverlay.ts`): a scrolling RMS/dB envelope of the sample bus (`SampleEngine.tapMaster`; oscillators aren't tapped) with a marker at every loop-seam crossfade — a dip ON a seam is a sample/seam-data problem, BETWEEN seams a crossfade-curve problem — plus per-frame max velocity and max poly AT of the held keys on the same 0–127 axis. For a Lumatone strike the velocity plotted and labeled is the **input velocity**: the hardware velocity after the key's press-time scale, which is what goes into the Lumatone curve and is that curve's x-axis in Calibrate Keys (`velocityCal.strikeOf`, recorded at note-on). It does not depend on the curve. The label adds the press time in ticks the device reported, decoded from the raw velocity (`pressTicksLabel`): `v124.2 (1t)` on a scaled key, `v112 (16t)` on an unscaled one. Any other voice shows the velocity it sounds at, alone.
- **Analysis**: two checkbox columns of four — Show analysis / coordinates / factors / Short intervals, and Show staff notation / Dark staff notation / Composer view / HEJI accidentals.
- **Recording**: the Rec/Play, Save/Load .hkr and Export/Import .mid button pairs, then one column of status pill · Export to Composer · Capture audio (`.rec-stack`).
- **Lumatone**: connection status · Auto-sync + sync pill · the two pedal-role selectors (Expr, Sus) side by side, stacked in one column; beside it a second column of Key effects, Calibrate Keys and Calibrate Pedal (all `luma-conn-only`, so they show only when connected). Calibrate Keys is never checked while hidden: `midi/engine.ts` reports each flip of the connected state (`setLumatoneConnectionHandler`, fired where the `lumatone-connected` class changes), and init.ts unchecks the box and closes the overlay on a disconnect, then re-checks and reopens it on connect when `prefs.calibrateKeys` is set. The pref itself is untouched by a disconnect, and at startup it opens nothing until a Lumatone connects.
- **Piano**: status + Device selector, and the Piano input / output / Valid ref bounds checkbox column.
- **Composer** (only while connected): connection status · Sync to Composer · score layout + match indicator on one row.
- Every group has the same fixed 87px height (three stacked select rows), so switching tabs never moves the canvas.

### Layout builder

A shallow tray (`#layoutBuilder`, `apps/hkl/src/ui/layoutBuilder.ts`) for the 48 layouts the bound allows (architecture.md → Note-name mapping), opened by **Custom…** at the bottom of the Mapping dropdown, on the current layout.

- **Non-modal.** It is a `<dialog>` opened with `show()`, not `showModal()`: no backdrop, and nothing outside it is blocked. It shares the modal trays' look (`dialog.hkl-dialog`), hangs from the top edge over the title row (`position:fixed`; a non-modal dialog is `absolute` by default), ends above the toolbars and the lattice, and casts a drop shadow in place of a backdrop.
- **Controls**: Octave division (3 / 4 / 6 / 12), Shear (− / + buttons, disabled at the bound) and Invert, stacked. Every edit calls `applyMapping(mappingOf(spec))` at once, so the lattice is the readout. After a division or invert change the shear is clamped to the nearest valid value (`clampShear`).
- **No preset picker of its own** (Max, 2026-11-09): the tray ends above the toolbars, so the Mapping dropdown stays in view and does that job. Choosing a preset there shows its three values in the open tray, and the dropdown names the preset whenever the tray's values match one; otherwise it reads Custom…. That follows from the id rule: `mappingOf` returns the preset's name for a preset's values.
- **Axis intervals**: Rows `(1, 0)`, Columns `(0, 1)` and Diagonal `(−1, 1)`, each named from its semitone count (`coordToMidi`): the spelling it has inside a band, or a neutral name where a band spells it two ways (semitone, tritone); a falling step reads "descending …".
- **No state of its own.** Every control is redrawn from `tuning.mapping` by `syncLayoutBuilder()`, which `applyMapping` calls, so a layout arriving from a recording, Composer or Reset shows in an open tray.
- **Focus.** Opening the tray and every edit blur the control, as the toolbar's selects do, so QWERTY keys keep playing (a focused select swallows them, `input/keyboard-notes.ts`). Escape closes the tray from anywhere unless a modal is open; closing keeps the layout.
- **Carriers.** A custom id is stored in prefs, a recording's snapshot (`.hkr`; the MPE `.mid` round-trip takes its layout from that snapshot) and the overlay snapshot, and accepted from bridge messages. A build from before 2026-11-09 rejects a `.hkr` recorded on a custom layout. A score never carries one: Composer converts from a custom layout, and Export to Composer writes Chromatic or Park (`.hkr` → `.hkc` transcription → Pipeline).
- **Gate**: `test/layout-presets/tray.mjs` (needs `pnpm dev`; muted headless Chromium) drives the tray through all 48 layouts with its own controls and checks them against the shared model.

### Keyboard shortcuts

- **Ref note**: set via **Ctrl+click** on any hex — lattice tweens to put that ref exactly at the outline center, banded or unbanded, so its position in its band picks the seam alignment under the keyboard. Ctrl+click on the current effective ref clears the selection (Ctrl+click and Composer cursor note). Every ref change — click or Composer message — re-centers through one fan-out (`state/reference.ts` → `effects/onRefChanged`; docs/architecture.md → Ref-driven layout shift).
- **Ref-edit modifier** (`input/ref-edit.ts`): Ctrl is one modifier for every input, held while any of its sources holds it (`setRefEditSource`: the computer keyboard's Ctrl, reported by `ui/keyboard.ts`; a window blur drops only that source). While it is held, the canvas dims every cell that cannot be a ref (and with **Key effects** on the Lumatone dims the same keys: Lumatone output → *Key effects*), a click picks the ref whether or not the event carries `ctrlKey`, and **a Lumatone key press picks the cell under the key** instead of playing it. All of them run one body, `pickRef(q, r)` (`input/ref-pick.ts`: validate, clear when the cell is the current ref, slide, persist `manualRef`), so a key press does exactly what a Ctrl+click on that cell does. The pressed key is never a note (`midi/handler.ts` returns before the velocity statistics, the Composer strike and `pressHeld`), so its note-off and aftertouch find no held record and do nothing; keys already held keep sounding and migrate with the ref change. QWERTY and piano-input keys stay notes while it is held. The state module has no imports because `render/draw.ts` reads it and is part of the lean overlay build, and `lumatone/sync.ts` reads it and is loaded without a DOM by its gate; what a change of the modifier causes (redraw, Lumatone color sync) is the listener `ui/init.ts` registers (`setRefEditListener`). The pick body, which reaches `effects/onRefChanged`, is a separate module for the same reason. Gate: `test/hkl-midi/ref-press.mjs`.
- **Hotkeys**: `Shift+\` toggles Calibrate Keys (listener registered at startup by `setLumaDiagHotkeyCallback`, `lumatone/lumadiag.ts`), with or without a Lumatone connected: it is the one way to open the overlay while the checkbox is hidden; while the Diagnostics overlay is open, `Ctrl+D` freezes its trace (overriding the browser's bookmark shortcut) and `Shift+D` dumps it to the console (`audio/diagnostics/loopOverlay.ts`). ### Ref-driven layout animation (500ms)

- Smoothstep position easing via `apps/hkl/src/render/animation.ts:tweenTo(targetQ, targetR)`. View center (`viewQ`, `viewR`) animates old→new on every ref change.

### Note naming

- `fifthName(r)` algorithmically computes names for any fifths distance. Labels render via a single Bravura SMuFL path (`drawHejiLabel` in `apps/hkl/src/render/keys.ts`, reached through `drawKeyLabel`): sans-serif letter + Bravura combined-glyph chain at 1.8× with shrink-to-fit (`scale = min(1, hexR×1.3 / totalW)`). The chain is built by `hejiLabel()` in `apps/hkl/src/tuning/heji.ts` — bare accidentals when HEJI off, accidental+arrows + septimal hooks when on.
- `drawNoteName` early-returns until `bravuraLoaded` (bundled `public/BravuraText.woff2` resolves on first paint), so the lattice paints nothing pre-load rather than flashing a Unicode chain.
- **Exponent collapse** (`COLLAPSE_THRESHOLD = 4`): when |AD| or |SD| > 4, `hejiLabel()` emits exponent groups (`HejiLabel.collapses`, at most two) — each one accidental-form glyph + sans-serif superscript count, drawn `before` or `after` the chain. Two steps, in order, each on what the one before left:
  - **Pairing** (both |AD|>4 AND |SD|>4): one group, position `before`. The unit is accidental + 1 arrow unless that would strand an excess above 4 on one side; that side then doubles in the unit: accidental + 2 arrows when the arrows exceed (9 flats, 14 up arrows → `(♭↑↑)⁷ 𝄫`; unbanded Ptolemaic), double accidental + 1 arrow when the accidentals do (10 sharps, 5 down arrows → `(𝄪↓)⁵`; unbanded Schismatic). `k = min(⌊|AD| / accidentals per unit⌋, ⌊|SD| / arrows per unit⌋)`.
  - **Excess** (the remaining |AD−SD|>4, greedy): `k = ||AD|−|SD||` absorbs it. |SD|>|AD| → natural+1 arrow, `before`; |AD|>|SD| → bare accidental, `after`. This is the only group when one count started at 4 or less, and a second group when the counts are beyond 2:1 after pairing.
  - The rest (equal residual AD/SD, or a difference of at most 4) goes to the chain: at most 4 glyphs (`test/unbanded/oracle.mjs` O).
- Septimal hooks always sit at the very end regardless of collapse position: one or two as glyphs (single U+E2DE/E2DF, two-hook U+E2E0/E2E1), more than two (`HOOK_COLLAPSE_THRESHOLD = 2`; only the unbanded Septimal layout stacks them) as one hook carrying a superscript `hookCount`. Composer's ±3 entry gate is unaffected — collapse is lattice-only (Composer draws the full chain). Placement: BravuraText draws each up hook lower than its down twin at the same ink height, so `SEPT_UP_RAISE` lifts it to the down hook's vertical ink extent (font units read from the .otf); the hooks start after the previous glyph's ink, since a down arrow hangs past its accidental's bare slot (natural ↓ by 0.057 em).

### Short intervals mode

`shortenInterval(name)` post-processor, three phases:
1. Multi-word phrases (syntonic/septimal/Pythagorean comma → SC/7C/PC, septimal diesis → 7D, chromatic semitone → A1, Pythagorean → P). An octave follows the rules of a 4th or 5th: after a quality word ("perfect octave", "lesser diminished octave") it becomes "8th" here, so it shortens as a quality and a number (`P8`, `<d8`), and phase 3 restores the P after a bare 7 or W for 4, 5 and 8 alike (`WP5`). Only a bare octave, an addend ("octave + syntonic comma"), becomes `P8` by itself in phase 2; before 2026-11-17 both applied, giving `PP8` and `dP8`.
1b. A multiple quality (Max, 2026-11-19): doubly augmented → `AA`, doubly diminished → `dd`, and from three on the count before the letter, 3× augmented → `3A` (`PAA1`, `Pdd8`, `P5A4`, `P12d5`). Before, "doubly" had no short form (`PdoublyA1`) and the count kept its × (`P5×A4`), which read as two intervals multiplied. The × stays on what is counted: commas and octaves (`6×SC`, `2×P8`). Every name with a multiple quality begins with "Pythagorean", and "septimal" only ever joins one as an added comma, so a count never meets the septimal `7`. Known and left: a seven-fold quality (`P7d5`) is a septimal form (`7d5`) behind a `P`.
1c. acute → `>>`, grave → `<<` (Max, 2026-11-19; they had no short form): `>>M3`, `<<m3`. "Acute" is only said of a major 2nd, 3rd or 6th and "grave" of a minor 3rd, 6th or 7th, none of which has a lesser or greater name. An acute major interval is two syntonic commas wider than the plain 5-limit one (one wider than the Pythagorean), a grave minor two narrower: the doubled sign is the two commas.
2. Word-by-word abbreviations (P/m/M/d/A, subminor→sm, supermajor→SM, harmonic→7m, septimal→7, lesser→<, greater→>, wolf→W, ordinals→cardinals, Ds/Sc/D/A/C). `sm` and `SM` (Max, 2026-11-18: `7sm2`, `7SM7`) are held by no other short form.
3. Structural cleanup (strip spaces, re-insert around ±). The P restored after a bare 7 or W before 4, 5 or 8 (`7P4`, `WP5`) applies only where the 7 or W starts the quality: until 2026-11-19 it also fired inside a count (`P7A8`) and inside an interval's number, so the 74th, 75th and 78th came out as `PA7P4`.

Uses HTML entities for lesser/greater glyphs.

### Interval naming

Every 5/7-limit interval is named `<base interval> ± commas`, where the **base comes from the diatonic spelling of the endpoints**, never from ratio shopping. Enharmonic-equivalent ratios are named by how they're written (F#→D is always a 6th); V-mode band-crossings surface their schisma additively. → rationale in `decisions.md`.

**Algorithm** (`apps/hkl/src/tuning/intervals.ts`):
1. `classifyDiatonic(q1,r1,q2,r2, layout)` → `{ord, qual, extraOct}` from `noteName`+`keyOctave` letter distance + 12-TET semitones (same logic as `equalIntervalName`). `layout` is the spelling's `{mapping, anchor, banded}` (a `TuningStateLike` serves), since the unbanded spelling depends on the anchor.
2. `pythagRefExp(ord, qual)` → closed-form Pythagorean prime-exponent vector (no table; from natural fifths-position + apotome stacks).
3. `jiRatioWithState` → actual exponent vector, as the difference of the two endpoints' `coordExps` (the canonical per-cell exp vector in `@hkl/shared/freq.js`, which also backs `freqAt`); mode shifts + V-mode schisma stacking live there, so frequency and ratio can't drift.
4. Difference vector → `solveCommas` → `(s, z, h)` syntonic/septimal/schisma counts.
5. `findBaseName(ord, qual, s, z)` picks the **nearest** override: enumerates all `(ord,qual)` overrides + Pythagorean default at `(0,0)`, scores by `|s−s_o| + |z−z_o|`, emits residual as commas. Ties prefer 5-limit (`z_o=0`) over septimal, and any override over the Pythagorean default. (So `(3,M,s=−2)` → "major 3rd − syntonic comma", not "Pythagorean major 3rd − 2× SC".)
6. Schisma `h` always renders as a suffix; never absorbed into the base.
7. `fmtInterval` handles compound ordinals and octave-prefix forms ("2 octaves + apotome").

**Override table** (`PAIRS`): array of complement-pair declarations. Each declares one half (`c1`); the other (`c2`) auto-mirrors via `autoMirror`, which swaps ord suffix (3rd↔6th), quality word (major↔minor, augmented↔diminished), and the adjective pairs **lesser↔greater** and **acute↔grave**. An explicit `mirror:` field overrides auto-mirror for class-specific phrases (apotome, harmonic 7th, chromatic semitone, diminished octave, subminor/supermajor). `c2` is **optional** — single-class declarations for classes whose complement is structurally unreachable (e.g. `(8,A)`, whose complement `(1,d)` never normalizes out of `classifyDiatonic`).

**Naming conventions** (fixed-meaning adjectives, never positional):

| Adjective | Meaning |
|---|---|
| `lesser`/`greater` | Two variants of a quality one SC apart; `greater` = higher cents. In the 5-limit (z=0) both are common and both carry the word: lesser/greater augmented 4th. In the septimal tritones the simple ratio keeps plain `septimal` (10:7, 7:5) and only the one a comma outside it is marked: **greater septimal augmented 4th** (81:56), **lesser septimal diminished 5th** (112:81) (Max, 2026-11-18). |
| `acute`/`grave` | One-SC variant on the *opposite* side of a 5-limit-common interval (exotic). e.g. acute major 2nd (729:640 vs common 10:9), grave minor 7th (1280:729). |
| `septimal` | One prime-7 factor vs the base: one septimal comma from the Pythagorean ref in the major/minor/perfect classes (9:7, 7:6), from the common 5-limit form in the augmented/diminished classes and the minor 2nd (15:14, 10:7, 21:20). |
| `subminor`/`supermajor` | The (2,m)/(7,M) extension capturing 28:27 / 27:14. Explicit mirror required (word-boundary regex won't transform it). |
| `wolf` | The narrowing 5-limit P-class variants: wolf 4th (27:20), wolf 5th (40:27). Widening-direction P-class has no override — surfaces as "perfect X + syntonic comma". |

**Septimal ratio assignment** (HKL-specific): most follow xen-wiki (`septimal minor 3rd`=7:6, `septimal major 3rd`=9:7, `harmonic 7th`=7:4, `septimal augmented 4th`=10:7, `septimal diminished 5th`=7:5). One pair departs from the canonical ratio, keeping the augmented/diminished classes' (s=∓1, z=±1) position (→ rationale in `decisions.md`):

| Name | HKL ratio | Canonical (xen-wiki) |
|---|---|---|
| septimal augmented 2nd | 135:112 | 25:21 |
| septimal diminished 7th | 224:135 | (mirror of 25:21) |

The Pythagorean-plus-septimal-comma tritones have names of their own (Max, 2026-11-18; they read "septimal augmented 4th + syntonic comma" before): 81:56 is the greater septimal augmented 4th (`>7A4`) and 112:81 the lesser septimal diminished 5th (`<7d5`), one `PAIRS` entry (`s: 0, z: +1` in the augmented 4th class) and its auto-mirror. Gate: `test/interval-names/short-forms.mjs` (pure Node) names every pair of keys over all eight mappings, the seven JI modes, banded and unbanded (5,929 names), and checks that no two share a short form, the `sm`/`SM` forms, and these two names and their complement.

**Notable spellings**: 9:8 = "Pythagorean major 2nd"; 10:9 = "major 2nd"; 16:9 = "Pythagorean minor 7th"; 9:5 = "minor 7th"; 4096:2187 = "Pythagorean diminished octave"; 531441:524288 = "Pythagorean comma" (via `pythag2` on the `(7,A)↔(2,d)` pair). Pure octave multiples: "perfect octave" (2:1), "perfect 15th" (4:1), "perfect 22nd" (8:1).

**Comma basis**: syntonic 81/80, septimal 64/63, schisma 32805/32768 (3 linearly independent commas spanning the 5/7-limit lattice). Output sticks with primary commas to match HEJI accidental semantics.

**Verification tooling**: `tools/interval-names/enumerate.ts` enumerates every Lumatone key pair in a mode, grouping (ord,qual,s,z,h) by taxicab distance (finds naming gaps); `tools/interval-names/smoke.ts` runs representative cases per mode.

### Lumatone output

**Auto-sync** (checkbox + status badge):
- On every color-affecting state change, `syncLumatoneColors()` computes the 280-entry target, diffs against tracked `deviceColors`, queues only changes. While a hidden game runs, each key's target passes through the game's scene last (`gameLedColor`: darkened, and blended toward white by the share of its tile under the scene's shapes; Internal subsystems → Hidden games), on both transports.
- **Two transports, chosen by firmware** (`lumatone.firmware`, from the connect-time `0x31` query; `frameSyncActive()`):
  - **1.5.0+: whole-keyboard frames.** Any difference sends one `0x55` frame of the full target (`buildFrameSysEx`); its deferred ACK sets all 280 `deviceColors`. Latest wins: `replaceQueue` swaps out a frame still waiting behind the one in flight, so at most one frame waits. Frames are ~17 ms each (p50, measured 2026-11-08), so the screen and the device move together. **Key effects** (the **Key effects** checkbox in the Lumatone group, `cbLumaKeyEffects` → pref `lumatoneKeyEffects`, `lumatone.keyEffects`; off by default): on this path each key shows the canvas's two per-key effects (`frameCellColor`), composed in the canvas's order. The `hoverKey`'s key is `lightenHex(color, HOVER_LIGHTEN)`, the canvas's own amount (`render/colors.ts`; the LED color is the same `hueC` variant the canvas lightens, so both change identically). While the ref-edit modifier is held, every key whose cell cannot be a ref (`isValidRef`, `state/reference.ts`: the same cells the canvas dims) keeps `REF_DIM_LED` (0.3) of each channel. That level is the device's own, set by eye and darker than the canvas's cover (`REF_DIM_FILL`, 50% of `#111`), which has note names to keep readable. Because the dim is part of the per-cell color, it follows a ref change and blends through the ref slide like any color. Triggers: `ui/init.ts` mousemove/mouseleave → `syncLumatoneKeyEffects()`, and the modifier's listener (`setRefEditListener`, registered in `ui/init.ts`) → `syncLumatoneKeyEffects('sync')`; the checkbox handler re-syncs at once, so toggling shows or clears the current effects. `lumaprobe.frames()` prints send→ACK and hover→ACK percentiles.
  - **Ref slide (frame path).** When the canvas slides (`onRefChanged` sees `animation.isAnimating` after `syncViewToOutline`), `beginLumatoneSlide(dq, dr)` eases a fractional device anchor from what the device shows to `kbAnchor` on the canvas tween's clock (`Date.now`), duration and `smoothstep` (exported from `render/animation.ts`). Its own raf tick builds a target per animation frame in which key *i* shows `sampleField(lumatoneCells[i] + anchor)`: the barycentric blend of the three cells around that lattice point (hex centers triangulate along each rhombus's m3 diagonal; the weights are affine-invariant, so (q, r) works under every alignment and mapping), blended in OKLab (`lumatone/oklab.ts`; LED values treated as linear light — the octave-board firmware has no brightness lookup table, though a computed curve isn't ruled out). OKLab keeps perceived lightness constant through the slide; blending the LED values directly read 3–5 L* brighter at every half-step between a dark and a light key, a visible pulse per lattice step (lessons.md). Frames go out latest-wins at the device's ~17 ms, so ~28 per slide; the landing frame is exact. A redirect starts from the interpolated anchor (no jump); a snap calls `cancelLumatoneSlide()`. `onRefChanged` decides slide-or-snap **before** the voice remap, whose color sync then sends the slide's first frame (identical to the device's state) instead of the final layout. The same sampler with a rotating sample point would animate an alignment change (exact 60° lattice rotations about the outline center), at about a second for 120°.
  - **Older firmware: the per-key `0x01` wipe below.** Until the version query answers, a connect starts on this path; a 1.5.0 answer re-syncs, which turns the queued per-key colors into one frame.
- **Empty diff while a push is running** still replaces the queue: colors queued behind the in-flight message are stale (hover left and came back before its ACK), and sending them would leave the device wrong.
- **Interleaved top-to-bottom wipe** (per-key path): `lumatone/sync-order.ts` ranks changed keys by physical Lumatone height (`2q + 7r`, descending), then left-to-right within a row. Always select a different SysEx board when another board has pending changes; sparse diffs may step ahead in the wipe to do so. Only repeat when all remaining changes belong to the same board. Routing honors the board-swap toggle; canvas rotation does not affect physical ordering. A replacement batch seeds this order from the in-flight board (or the last setup message when setup precedes colors).
- **In-flight race**: an awaiting-ACK SysEx's color (or an in-flight frame's 280 colors) is folded into the predicted snapshot so the diff accounts for the device's near-future state.
- **Queue swap, not restart**: a new sync replaces the queued colors without canceling the in-flight message (which finishes naturally); queued non-color messages (layout setup, control queries) keep their place ahead of the new batch. `sysex.cancel()` tears everything down when Auto-sync is turned off.
- **Preset switch on the device**: a preset button reloads the device's key map, key types and colors from the preset, board by board, and the firmware ends the switch with All Notes Off then Reset All Controllers on channel 1 (`B0 7B 00`, `B0 79 00`). `watchPresetSwitch` (`lumatone/sync.ts`, fed every inbound channel message by `midi/handler.ts`) re-pushes on the second message directly after the first: `resyncLumatoneDevice()` voids the in-flight color message (`sysex.voidInFlight()`: its ACK records nothing, since it may have arrived before a board's reload), clears `fixedLayoutSent` and `deviceColors`, and syncs, which is the connect-time push again (280 key writes, the two flags, the two velocity tables, the colors). Nothing is pushed before the pair, because a write that reaches a board before its reload is ACKed and then overwritten; so the preset's colors and key map are live from the switch until the re-push lands. With Auto-sync off, or a calibration running, nothing is sent and the next sync is a full one. HKL writes no preset slot and changes no device setting for this; held notes and note input during the switch are not touched. The Calibrate Keys board-swap toggle uses the same `resyncLumatoneDevice()`. Firmware trace: lessons.md → "Macro buttons in normal mode"; gates `test/hkl-midi/preset-resync.mjs`, `departure.mjs` (F2).
- **Velocity tables**: the device turns a key's press time (scan passes, "ticks") into a velocity through two tables it keeps in RAM, the press-time interval table (CMD `0x20`) and the velocity LUT (CMD `0x08`), and it reloads both from the preset file on a power cycle or a preset button. HKL's velocity curve means something only over tables HKL defines, so both are part of the setup batch above, sent with every connect and after every preset switch: the identity LUT (`velocityCal.buildIdentityLut`: the firmware's bin is then `127 − velocity`, the slowest bin sent as 1) and the table built from the interval curve's low / high / gamma (`velocityCal.buildIntervalTable`; default 1…127, one tick per velocity). Live state only: no preset slot is written (`0x09` is never sent), and with Auto-sync off neither table is sent, like the rest of the setup. A slider change reaches the device with **Push to Lumatone** or the next setup. `velocityCal.pressTicks(raw)` is the inverse, a raw velocity's press time as a tick range, which the Diagnostics overlay prints. Why they are pushed and not assumed: lessons.md → "The device ran its preset's velocity tables"; decisions.md 2026-11-22. Gate: `test/hkl-midi/velocity-tables.mjs`.

**On-connect setup** (first auto-sync after `findLumatone()`):
- 280 × `CHANGE_KEY_NOTE` (fixed MIDI layout)
- `SET_AFTERTOUCH_FLAG (0x0E) = 1`
- `SET_LIGHT_ON_KEYSTROKES (0x07) = 1`
- `queryFirmwareRevision()` (silent; logged)

**Pedal calibration**:
- Calibrate Pedal button toggles cal mode. Active: panel shows live ADC min/max (from CMD 0x3E packets) + valid flag. No CC4 readout (firmware suppresses CC4, sends 0x3E instead).
- Reset to Factory button sends CMD 0x39.
- Max debug logging while active (every 0x3E first+10th raw, every CC4 with timing, entry/exit). Outside cal mode: CC4 endpoints only.

### Lumatone input

`handleMidiMessage(e)` dispatches:

| Message | Handling |
|---|---|
| SysEx CMD 0x3E | calibration packet handler |
| SysEx CMD 0x33 reply | heartbeat ping reply — consumed (proof of life already recorded); never reaches the queue |
| Other SysEx | `sysexHandleResponse` (ACK matching) |
| CC 4 (expression) | `setJackPosition('expr', d2/127)` (a CC 4 of 0 or 1 reads as 0); what that does is the jack's role (*Pedal roles*, below). Verbose during cal; else endpoints (0/127) only. **The damper never raises a voice**: each sustained voice's `damperGain` follows `Voice.damperLevel = min(damperLevel, depth)` (`applyDamperToVoice`), a one-way ratchet reset only by a fresh voice (re-strike). Re-pressing after a partial lift holds the level; `sostenutoOn` holds locked voices where they are (it no longer pins them to 1.0). Gate: `test/hkl-midi/damper.mjs`. |
| CC 64 (sustain) | `setJackPosition('sus', d2≥64 ? 1 : 0)`; what that does is the jack's role (*Pedal roles*, below). |
| Note on/off | audio + selection; with the ref-edit modifier held, a note-on is a ref pick instead and never a note (Display → Ref-edit modifier); otherwise, while a hidden game runs, the game decides what a note-on is: swallowed, and not a note either, or a note at the velocity the game names; and it hears every note-off (Internal subsystems → Hidden games). Note-off branches on `sustainPedalDown ‖ sostenutoLockedKeys.has(key)`: keep or release. `sustainPedalDown` is `damperDepth > DAMPER_RELEASE_FLOOR`, the same threshold the release loop uses — so there is no depth band that defers a note-off the release loop would never claim. |
| Poly aftertouch (0xA0) | per-voice volume modulation. |
| Pitch bend (0xE0) | ignored (see *Departure detection* — it was tried as a power-off tell and removed). |

**Pedal roles** (`midi/pedals.ts`, state in `state/pedal.ts`). Each jack has a role of its own, chosen in its own dropdown (`#pedalExpr`, `#pedalSus` → prefs `pedalExpr`, `pedalSus`; both default to Sustain):

| Role | What the jack does |
|---|---|
| None | nothing (its CCs are still logged for the HUD) |
| Sostenuto | `sostenutoOn()` when the pedal goes down, `sostenutoOff()` when it comes up |
| Sustain | a damper source: `pedal.damper[jack]` = the pedal's position (continuous on Expr, 0 or 1 on Sus) |
| Ctrl | holds the ref-edit modifier (`setRefEditSource(jack, …)`; Display → Ref-edit modifier) |

- **One derivation.** `pedal.position[jack]` (where the pedal is, kept whatever the role) and `pedal.roles[jack]` are the only inputs; `applyJacks()` derives everything both jacks do and runs whenever either changes: a CC (`setJackPosition`), a dropdown (`setJackRole`), the device leaving or a forced clear (`releaseJacks`). A role changed while the pedal is down is therefore re-read from the pedal at once, with no transition written by hand. It lets go of what the jacks no longer hold before engaging what they hold now: a damper turned sostenuto releases its sustained notes and then catches only the keys still held.
- **Binary roles** (Sostenuto, Ctrl) read a pedal as down from CC 64 up, the sustain jack's own threshold. On the continuous Expr jack that is one threshold with no hysteresis, so a pedal resting exactly at its midpoint can chatter.
- **Both jacks may share a role.** Dampers combine by max; sostenuto and Ctrl are held while either pedal is down. The engine is told about the sostenuto only when the jacks' combined answer changes, so a pedal moving further down, or the second pedal joining, never snapshots the held keys again, and a sostenuto engaged by a recording playback is not the jacks' to release.
- **Damper sources.** `pedal.damper` has one entry per writer — `expr`, `sus`, `piano` (the piano-input device's own pedal), `composer` (Composer playback), `playback` (recording playback) — and `setDamperDepth()` takes their max, so no source can overwrite another's. Each writer releases its own entry when it goes away (Lumatone departure, the piano port being left, a playback stopping).
- Gate: `test/hkl-midi/pedal-roles.mjs`.

Note routing uses the **fixed MIDI layout**: stable (channel, note) per physical key. `fixedMidiToKey(ch, note)` converts at input time, through `layout/physical.ts` (key offset + kbAnchor) — channels 0–4 = the five board groups, notes 0–55 = key index within board.

#### Departure detection: the liveness heartbeat

Powering the Lumatone off emits a burst of spurious note-ons that never receive note-offs. They are
*protocol-valid* frames from a browning-out key scanner, byte-for-byte identical to real playing (lessons.md),
and nothing at runtime separates them from a dense, loud chord — velocity included (the burst is mostly but
not only velocity 127, and real fortissimo reaches 127 routinely). So the burst is **not filtered**: it
sounds, and is cleared once HKL notices the device is gone. On Firefox nothing else notices: `MIDIAccess` is
a snapshot that never reports the port vanishing. History of what was tried: decisions.md, 2026-09-21 and
2026-10-02.

**The heartbeat** (`midi/heartbeat.ts`, always on, no pref) pings the Lumatone (CMD 0x33 `LUMA_PING`) only
while the Lumatone is **holding something** — keys down (`heldCount('lumatone')`, `input/held.ts`), or `sustainPedalDown` /
`sostenutoActive` / the ref-edit modifier from its pedal jacks — **and** has sent nothing for `HEARTBEAT_QUIET_MS` (200).

- **Any inbound message on the port is proof of life** (`heartbeatInbound()` at the top of
  `handleMidiMessage`), so active playing sends no pings at all; it is the silence after the burst that
  triggers one. Ping replies stop there and never reach the SysEx queue.
- A reply within `HEARTBEAT_REPLY_TIMEOUT_MS` (250) clears the miss count; a held, motionless chord on a live
  device is pinged about every 200ms. Nothing held = no pings (nothing could be left stuck).
- **Jank is inconclusive, never a miss.** The reply is dispatched on our main thread, so a blocked thread
  looks like a silent device. The wait is ticked every 50ms; if any tick runs >75ms late the wait doesn't
  count and the ping is re-sent. `HEARTBEAT_MISSES_TO_DEPART` (2) clean misses in a row call
  `markLumatoneGone()`. Typical time from burst to release: ~0.7s. Verified on hardware for both a held
  chord and the burst itself.
- **Known, accepted gap:** powered off with nothing held, the heartbeat isn't running, so the badge keeps
  reading "connected" until a re-check (status-badge click). Nothing can be stuck in that case.
- **Cost to the device**: the firmware runs one single-threaded loop (MIDI intake → PIC scan → pedals → wheel)
  with the MIDI port non-blocking; `sysexResponsePing` is a preamble fill + one `write()`, no PIC traffic — a
  strict subset of an LED update, which color sync sends at ~300/s. Verified on hardware at 50 pings/s with
  no effect on playing.

**`markLumatoneGone()`** (`midi/engine.ts`) then:

1. **nulls `midiIn.onmidimessage`** so nothing still in flight can latch.
2. nulls `midiOut`/`midiIn`, cancels the SysEx queue, forgets `deviceColors` /
   `fixedLayoutSent`, sets `pendingReconnect`, and updates the status indicator. This happens **before**
   step 3, so a failure there cannot leave the badge claiming the device is still connected.
3. calls `releaseLumatoneInput()` (registered via `setLumatoneLostHandler` to avoid an import cycle), wrapped
   so a throw is logged rather than swallowed. It stops the heartbeat, drops every held Lumatone key
   (`dropHeld('lumatone')`, `input/held.ts`) from `selectedKeys` / `sustainedKeys` / `keyVelocity` /
   `aftertouchSnapshot` / `paFilter`, **and forces
   the pedals released** (`releaseJacks()`: both positions to 0, then the roles let go of the damper, a
   sostenuto, the ref-edit modifier) — CC 4 / CC 64 come from the Lumatone's own jacks, so whatever a jack
   was holding would otherwise stay held forever. A damper held by another source is not touched.
   Mouse/computer-keyboard voices are untouched.

The same `releaseLumatoneInput()` runs from `findLumatone`'s port-loss branch, which is how Chromium reaches
it via `statechange`. Nulling `midiOut` re-arms the hotplug poll (whose "skip while the Lumatone toolbar is
hidden" gate is bypassed while a self-declared departure is pending).

**Re-adoption is confirmed, not assumed.** Firefox's fresh `MIDIAccess` keeps listing a powered-off Lumatone
as connected while its USB link lingers, so while `pendingReconnect` is set a port that (re)appears is only a
**candidate** (`confirmCandidate`): HKL pings it and adopts it only on a ping reply (a straggling note does
not count), otherwise drops it after 500ms and the next poll tick asks again. A false departure therefore
costs a brief dropout, and a dead device can't be re-adopted as "connected".

**Re-checks swap port objects cleanly.** A re-check while connected (status-badge click) yields a fresh
`MIDIInput` object for the same port id; `findLumatone` detaches the old object before wiring the new one,
since both stay open and the browser delivers to every object with a handler.

**Gate**: `test/hkl-midi/departure.mjs` — 56 checks over departure, pedal release, badge state, the heartbeat
(idle / live / active-traffic / dead burst / dead pedal / jank), stale port objects, and confirmed
re-adoption. Run it before declaring any change to `midi/handler.ts`, `midi/heartbeat.ts` or
`midi/engine.ts` done.

**Instrument**: `apps/hkl/src/lumatone/probe.ts` exposes `lumaprobe.latency()` / `watch()` / `dump()` for
Lumatone round-trip and teardown timing (`watch()` is how the ~100ms BBB-death figure was measured). It
attaches its MIDI monitor only while a run is active.

### Piano output (external-synth JI playback)

`apps/hkl/src/midi/piano-out.ts`. The "Piano output" toggle (Piano tab) mirrors HKL playback to an external MIDI synth at true JI, even on synths with **no pitch bend / no MPE** (e.g. Korg SP-250).

**Mechanism**: such synths honor **RPN 0001 (channel fine tuning)**, ±100¢ over 14 bits (center 8192, 81.92 steps/cent). A note-on re-applies the channel's current fine-tune to every voice on that channel → distinct tunings need distinct channels. So **one voice per MIDI channel** (`MpeAllocator`, constructor-configurable channel range/reuse/exclusions). Piano output uses channels **1..16 minus 10 and 16** in **FIFO** order:
- ch 10 = GM percussion (note-on plays a drum map, not a pitch).
- ch 16 (this SP-250) ignores note-off and won't accept the RPN tune.
- FIFO lets a reused channel's release tail decay before reuse. → 14 melodic channels.

Per note-on: `keyFreq(q,r)` → nearest 12-TET note + cents (`freqToNoteFine`, A4=440) → RPN 0001 CCs → note-on, on that channel.

**Overflow guard**: keys evicted past the 14-voice cap go into a `shed` set (wanted but silent), skipped by the start loop until they leave `want` — newest 14 sound, no churn. `restrikePianoOut` drops a key from `shed` so a re-strike can re-compete. (Avoids the steal-oldest cascade of a naive membership diff.)

**Hook**: `syncPianoOut()` runs from `syncOutput()` tracking `selectedKeys ∪ sustainedKeys`. Self-gates on its own enabled flag, **independent of `audioEnabled`** — so muting Audio + enabling Piano output makes the external synth the sole source. Sustain needs no CC64 forwarding (HKL defers note-off until pedal release). Aftertouch not forwarded.

**Pedal capture**: a sustain pedal on the piano-input device sends CC 64 on the same port; `piano.ts`'s `pianoMessage` routes it (`handleSustainCC`) into its own damper source, `pedal.damper.piano`, via `setDamperDepth`. **Always acts as sustain** (continuous half-damper), independent of the Lumatone jacks' roles; it is released when the piano port is left or piano input is switched off. Feeds HKL's deferred note-off, so held JI notes ring on the external synth until release (matters with Local Control off).

**Rearticulation**: re-striking a pedal-held key doesn't change `selected ∪ sustained` membership, so the diff won't re-fire. `restrikePianoOut(key)` tears down the voice (note-off + free channel) at each re-strike, before the following `syncPianoOut()` re-acquires + re-strikes with updated velocity.

**Composer playback**: the bridge dispatch (`apps/hkl/src/bridge/hkl-side.ts`) drives the engine directly and calls `draw()` (not `onSelectionChanged`, to avoid echoing held-keys to Composer), so `syncPianoOut` is wired explicitly at each point the dispatch mutates `selectedKeys` + draws (chord attack, per-voice note-off timer, `abortActive`); `restrikePianoOut(k)` runs in the same-pitch back-to-back branch. Slur glides surface as note-off-old/note-on-new re-attack via the selection diff.

**Program mirroring**: each channel is an independent timbre slot. `pianoMessage` captures Program Change off the input port (regardless of input-enabled gate) and `setOutputProgram()` **broadcasts to all 16 channels** — on PC capture and after `open()` resolves, never per-note (the CH345 adapter drops bytes under burst). `currentProgram` is null until a PC is seen.

**Channel levels**: `broadcastChannelLevels()` forces every channel to CC7=100, CC11=127 on enable/rebind and after each PC (GM channels have independent volume/expression defaults that otherwise surface as note-to-note jumps).

**Local control**: `sendLocalControl(port, false)` (CC122=0, all channels) on enable/wire so raw 12-ET keys aren't heard; CC122=127 restores on disable / port switch / page close (`beforeunload`). CC122 may be a no-op on some units.

**Device**: output port **auto-matches the selected Piano input device by name** (`rebindPianoOut()` on enable, input-device change, MIDIAccess statechange) — no separate dropdown. The bound port is explicitly `open()`ed (Firefox doesn't open eagerly on `send()`). Requires the synth on Omni On / multi-timbral. Persisted via `pianoOutputEnabled`.

## Recording, playback & MIDI round-trip

HKL records every performance (Lumatone, QWERTY, mouse) as a stream of lattice-coordinate events, plays it back through `@hkl/engine`, and exchanges `.mid` files with external DAWs.

### Architecture

- **`.hkr` (JSON, source of truth)**: layout snapshot (tuning, mapping, anchor, banded, septimalW, instrument, `pedalMode`, A3 ref) + flat event list `[{t, k, q, r, …}]`. `banded` absent in older files → true. Wherever the layout reads the anchor (Syntonic/Polysyntonic, any mode unbanded: `readsAnchor`) a note-on recorded after a mid-take re-anchor carries its own `a` (anchor); absent → the snapshot's (absent in older files → 0, which no older mode reads). Playback pins the live anchor per note-on (`setAnchorOverride`) and releases it on stop; MPE export reads the same field. Version-stamped (`format:"hkr", version:1`); event kinds `on/off/pa/cc4/cc64/warn` keyed by `k`. **The two pedal streams record what the pedals did, not which jack or device did it**: `cc4` is the damper depth (the max over every damper source) and `cc64` is the sostenuto, whatever the jacks' roles; a pedal in the Ctrl role records nothing. The names are the file format's, from when each stream mirrored one jack. Every take is written with `pedalMode: 'sostenuto'`, which says exactly that; `'sustain'` marks an older take made with the former single Pedals dropdown on Sustain, where `cc64` is a second, binary damper (`recording/types.ts`). The format and its version are unchanged, so either build plays either file. Timing is `audioCtxSec` from `epoch=0` (the engine's ramp-schedule clock). No back-compat with pre-legacy-purge files.
- **`.mid` (binary, derived)**: exported/re-imported deterministically against the same snapshot. The two files travel **separately** — not bundled.
- **MPE export**: single-track format-0. Channel 1 = manager (CC4/CC64 + MPE Configuration Message); channels 2–16 = members (one voice each). Per-member pitch-bend range ±48 semitones via RPN 0. Tempo fixed 120 BPM, PPQ 960.
- **MIDI → `.hkr` inverse**: requires the originating snapshot (UI prompts "Load matching .hkr first"). Builds a frequency index over the lattice under the snapshot's tuning; each noteOn's `(note, channel-bend)` → frequency → nearest-match. 25-cent sanity gate; farther emits a `warn` event.

### Capture point

Hooks live **inside `@hkl/engine`**, not at the MIDI input handler — the convergence point for every source (Lumatone notes after `(channel,note)→(q,r)`, QWERTY, canvas clicks all flow through `noteOn`/`noteOff` before sounding). One line per engine entry point catches everything. Damper and sostenuto capture (`cc4` / `cc64`) in `setDamperDepth` + `sostenutoOn/Off`; poly aftertouch in `handleAftertouch`. Hooks short-circuit when `audioEnabled === false` — silent input is not recorded (intentional; recording without audio is meaningless).

### Playback

Web-Audio look-ahead scheduler (Chris-Wilson pattern): 25 ms `setTimeout` loop walks events within the next 100 ms window vs `audioCtx.currentTime`, schedules a per-event `setTimeout` to dispatch on time. Dispatch routes per `k`:

| Kind | Action |
|---|---|
| `on` | `noteOn` + add to ledger + add to `selectedKeys` + `draw()` |
| `off` | `noteOff` + remove from ledger + remove from `selectedKeys` + `draw()` |
| `pa` | `handleAftertouch` |
| `cc4` | the take's damper → `pedal.damper.playback`; `setDamperDepth()` |
| `cc64` | per the take's own `pedalMode`: `sostenutoOn/Off` (`'sostenuto'`), or a second damper stream, the deeper of the two holding (`'sustain'`) |

- **Ledger** (`playbackKeys: Set<KeyId>`) tracks playback-created voices only — stopPlayback releases those, leaving user-held voices alone. Live input is allowed during playback and mixes in.
- Applying the snapshot at play-start drives the real control handlers (`setTuning`, `changeWaveform`) so all side effects fire (color sync, info refresh, prefs). Sample instruments awaited if not loaded. The pedal jacks' roles are never part of it: `pedalMode` is read from the take by the dispatch above and has no live counterpart (`snapshotMatchesLive` ignores it), so live pedals keep their roles and mix with the take's.
- **Stopping lets go of the take's pedals**: the playback damper source goes to 0 and a sostenuto the take engaged is released. Nothing live writes that source, so a take ending with the pedal down would otherwise hold it.

### Transport

Three mutually-exclusive states `idle | recording | playing`. State lives module-private in `apps/hkl/src/recording/capture.ts` + `playback.ts`; UI in `apps/hkl/src/ui/recorder.ts` reads via `isRecording()` / `isPlaying()`.

**Auto-balance**: starting Record emits synthetic `on` at t=0 for held voices; stopping emits synthetic `off` for still-held voices → the recording is self-balanced, no stuck notes on playback.

### UI

Toolbar group after the Lumatone block: Rec / Play / Save .hkr / Load .hkr / Export .mid / Import .mid + a `recording-status` pill ("Idle" / "Recording 0:04" / "Playing 0:02 / 0:18" / "Loaded 0:18"; also "Preparing…", "Load failed: …", and "Enable Audio first" — Rec and Play need Audio on). Timer runs only while state ≠ idle (`requestAnimationFrame`).

`?hklrec=1` exposes `window.__hkl_rec` with `getSession()`, `setSession(s)`, `selfTestRoundTrip()` for DevTools verification.

### Audio capture (sidecar .wav)

Independent of `.hkr` capture. A "Capture audio" toggle brackets the master-bus output of every record/playback span and downloads a 44.1 kHz / 16-bit stereo `.wav` (`hkl-<isoStamp>.wav`). The tap is an `AudioWorkletNode` (`apps/hkl/src/audio/capture-worklet.js`) as a parallel sink off `limiter` (`limiter → destination` untouched; `limiter → captureNode` runs alongside). The worklet posts stereo Float32 frames; `apps/hkl/src/audio/capture.ts` accumulates and calls `encodeWav16()` in `apps/hkl/src/audio/wav.ts` on stop.

The span ends 1.5 s after Stop/playback-end so release tails land. `.wav` is a separate download (same isoStamp), faithful to the engine output (post high-shelf, post limiter) where a `.hkr` re-render through a non-HKL synth would not be.

### Out of scope for v1

- **Layout change mid-record**: detected; emits one `warn` on first divergence, then continues against the original snapshot.
- **Paused playback**: none.
- **Bundled `.hkr` + `.mid`**: stay separate.
- **Tempo / time signature in `.hkr`**: not modeled (MIDI export uses fixed 120 BPM 4/4 for DAW quantizers).
- **Composer export (`.hkc`)**: see below.

## `.hkr` → `.hkc` transcription

Takes a `.hkr` recorded at roughly constant tempo in a user-supplied time signature, produces a Composer-native `.hkc` (MEI 5) colored-notehead grand staff — downloadable or sent straight to Composer over the bridge for editing. **v1 scope**: 8th-note minimum granularity, middle-C voice split, no microtonal accidentals (12-TET notation; lattice spelling from `noteName(q,r)` gives the enharmonics). The `.ly`/LilyPond emitter it replaced is gone.

### Pipeline

**Frame first (`index.ts`, `inScoreFrame`)**: a score's mapping is one of the eight presets, so a recording made on a custom layout is re-expressed before anything else runs: every `on` cell through `convertNote` (docs/architecture.md → Note conversion; the whole lattice, a recording having no outline) into Chromatic (plain layout) or Park (inverted), the finest preset of its orientation, with the snapshot's home band and any per-note `a` carried into that frame; an `off` or `pa` follows its `on` to the key it went to. Best effort, with no guard (Max, 2026-11-09). Measured over the 40 custom layouts: a plain layout converts exactly in every tuning, banded and unbanded; an inverted one exactly from division 3 or 6, and from division 4 or 12 only banded in Equal / Ptolemaic / Pythagorean / Semiditonal / Septimal (their exact frame would be an inverted Chromatic, which is not a preset). A preset recording is untouched and comes out in its own mapping.

`.hkr` → onsets → tempo → beats → meter → chords → qnotes → voiced → `.hkc`. Eleven modules under `apps/hkl/src/transcription/`, one per stage. Identity (`Onset.id`, `QNote.sourceOnsetIds`) flows end-to-end for a future correction UI; each `QNote` also carries a `coords: {q,r}[]` array (parallel to `pitches`) so the emitter spells from the exact lattice cell rather than a MIDI-only guess.

**Tempo (`tempo.ts`)**: IOI autocorrelation on a 10 ms binned onset envelope, weighted by a log-Gaussian prior peaked at 100 BPM (σ=0.3 log). A BPM hint hard-constrains the lag search to ±15% of the hint period. Parabolic peak interpolation for sub-bin resolution. Octave (half/double) errors are the standard failure mode — mitigated, not eliminated.

**Beats (`beats.ts`)**: Ellis-style DP — `C(t) = s(t) + max(0, max_{t'∈[t−dMax, t−dMin]} C(t') − λ(t−t'−T)²)`, T = target period, `dMin/dMax` = ±50% of T, `λ = 0.5`. Traceback from the highest-scoring beat in the final T-window.

**Meter / downbeat (`meter.ts` + `quantize.ts`)**: phase search over `numerator` offsets — for each phase ∈ [0, numerator), sum onset strength near beats whose index ≡ phase (mod numerator); pick the max. In `quantize.ts` the chosen phase's beat time is extrapolated **backward by whole bars** until the tick origin ≤ the first onset's time, so leading notes land as a bar-0 pickup rather than being clipped.

**Chords (`chords.ts`)**: cluster onsets whose `t` is within 30 ms of the **first** member of the current cluster (not the last — "last" allows transitive drift and over-groups fast runs). Representative `t` = median; `tOff` = max.

**Duration quantization (`quantize.ts`)** — the load-bearing module. Per-bar Viterbi DP over an allowed atom set (64th-note ticks at `subdivisions: 32`/quarter):

| Atom | Ticks | Notation base | Complexity |
|---|---|---|---|
| 8th | 16 | `8` | 0.10 |
| quarter | 32 | `4` | 0.00 |
| dotted quarter | 48 | `4.` | 0.30 |
| half | 64 | `2` | 0.05 |
| dotted half | 96 | `2.` | 0.35 |
| whole | 128 | `1` | 0.10 |

(v1 omits 16ths/32nds.) Position snaps to a 16-tick (one-8th) grid. Per bar, the DP fills `(startTick, durTicks)` with atoms minimizing:

```
total_cost = Σ atom.complexity + Σ TIE_COST × (atoms − 1) + Σ boundary_penalty(atom)
```

- **`TIE_COST = 0.40`** — calibrated so single-atom notations beat tied chains at clean alignments, but ties win where they should (a half from beat 2 of 4/4 prefers `quarter + quarter tied`).
- **Boundary penalty** = `0.05 × (worst_metric_weight_inside_duration − start_weight)`. Metric weights: bar start 100, bar middle (4/4) 50, beat 25, 8th 8, 16th 6.
- **Rest insertion**: if a chord's release-tick is ≥ 16 ticks before the next onset, a rest fills the gap; below that, the silent time folds into the preceding note's duration.

**Voicing (`voicing.ts`)**: middle-C (MIDI 60) threshold per chord. All-treble/all-bass → one staff; mixed → split (≥60 to treble voice 1 staff 1, <60 to bass voice 1 staff 2, same `startTick`). **Rest consolidation** runs after the split: consecutive `isRest` QNotes merge per voice, slice at bar boundaries, re-fed through `splitDuration` so an all-rest bar collapses to `r1` instead of mirroring the active staff's rhythm. → see `lessons.md` "Rest consolidation in voicing fixes the 'mirroring' bug."

**MEI emission (`meiEmit.ts`)**: builds the `.hkc` via the shared `@hkl/notation/mei-build` builder — the single source of truth for the `.hkc` dialect, shared with Composer's model (`emptyMeiDoc`, `buildNoteElement`/`buildChordElement`/`buildRestElement` all live there now; Composer re-exports them). `emitMei` reuses the head/`hkl:config`/scoreDef skeleton (`layoutReq.tuningMode` from the recording's snapshot, `refQ/refR = 0,0`), then appends one `<measure>` per bar: treble → staff 1 / layer 1, bass → staff 2 / layer 1 (layer 2 left empty; Composer fills placeholders on load). Each note carries `data-q`/`data-r` + a pre-darkened `color`; spelling reuses `noteName(q,r)` + `keyOctave(q,r)` from `@hkl/shared/notes.js` (sharps on +r, flats on −r; no key-signature inference in v1). **Ties**: a sustained note split across atoms — within a `QNote` or across a bar line (where `quantize` marks the previous QNote's trailing atom tied) — becomes an MEI `@tie` chain (`i`/`m`/`t`) on each note; `data-tie-partner` is left for Composer's `normalizeTies`, which runs on load via `replaceDocument`.

**UI / transports**: "Export to Composer" opens a modal (title, time-sig numerator 1–12, default 4 / denominator fixed at 4, optional BPM hint 40–240) with two actions — **Download `.hkc`** (`downloadBlob`, always available) and **Send to Composer** (gated on a live bridge connection: `isComposerConnected()`; disabled with an explanatory toast otherwise — no silent download fallback). Send dispatches the `import-score` `HklEvent` (`{ type, mei }`); Composer confirms-if-dirty then `replaceDocument` + adopts the score's `layoutReq`. `?hklrec=1` exposes `window.__hkl_rec.transcribe(opts)` returning `{ hkc, debug }` (debug = every intermediate IR: onsets, tempo, beats, meter, chords, qnotes, voiced).

**Round-trip test**: `pnpm test:transcription` (`test/transcription-roundtrip/run.mjs`, needs `pnpm dev`) is a two-page headless check — emit a `.hkc` from a synthetic recording on the HKL page, load it into the Composer page via `replaceDocument`, and assert measure count, per-note `data-q`/`data-r`/`color`, no tie orphans, placeholder invariant, origin spelling, and serialize round-trip stability.

**Color handling**: `darkColorHex(q,r)` in `apps/hkl/src/transcription/pitch.ts` calls the shared `inkColorHex` (`@hkl/shared/keycolor.js`, also Composer's): each hue's own ink (`hueC[…].ink`), a darker paper-readable color per hue (orange and yellow toward goldenrod, green yellow-green, teal toward cyan, pink toward magenta, so the pink/orange and teal/green confusion pairs on white stay distinguishable; the fourths cycle's dandelion and spring green have inks derived from those). Stem/flag/accidental color suppressed (only the notehead carries lattice color). Colors follow the live layout (`tuning.mode`/`mapping`/`anchor`), not each event's recorded anchor, so a Syntonic/Polysyntonic take re-anchored mid-recording is colored as the anchor stands at export.

**Out of scope for v1**: rubato/variable tempo, tuplets (triplets are the v2 target), time-sig change mid-piece, microtonal accidentals (HEJI via Ekmelily is a future path), manual correction UI (`sourceOnsetIds` preserved for it).

### Render pipeline

**Offscreen build** (on dirty flags):
- `hexCanvas`: colored hex fills for the extended grid (half steps warm-shifted in 7-limit, the octave cycle in Equal).
- `textCanvas`: note labels on transparent bg, scalable accidentals.

Dirty flags minimize rebuilds: tuning-mode change → hex layer; note names → text layer; resize/extend → both; ref-driven tweens pre-build the hex layer across `[view → target]` (`buildHexLayerForTween`). The two layers are blitted with one shared geometry (gridRef, pad, size), so `draw()` builds both at the same geometry: when a rebuild would move it (e.g. the first text-only rebuild after a tween's midpoint build), both rebuild (`builtGridKey`; gate `test/hkl-midi/layer-sync.mjs`).

**Key painters** (`render/keys.ts`): a key's hexagon path (`hexPath`, `hexSubpath`), its label (`drawKeyLabel`) and the band-seam segment between two adjacent keys (`seamSegment`: through their midpoint, square to the line joining them, 0.55 × `hexR` to each side), with the context and the key size (`hexR`, `hexScale`) as arguments. They read no canvas, geometry or tuning state, and use only path calls, `fillText`, `measureText`, `font`, `fillStyle`, `textAlign` and `textBaseline` (`KeyContext`), so a recorder that implements those can stand in for a canvas. `draw.ts` binds them to the context it is drawing into (`drawHexPath`, `hexSubpath`, `drawNoteName`, which keeps the `bravuraLoaded` gate) and takes its seam segments from `seamSegment`; the shape guide calls them directly (`shapes/diagram.ts`). Lifted out of `draw.ts` line for line on 2026-11-17: `layout-shots.mjs` before and after is 52/52 identical, and so are 56 further shots of every tuning mode at every hex size with HEJI on and off. Cost, as medians of seven rounds (Euler in Septimal with HEJI on), before and after: the label layer's rebuild 13.2 and 13.5 ms, the hex layer's 5.8 and 5.8 ms, a plain frame (which strokes the seams) 0.7 and 0.7 ms.

**Per-frame draw**:
1. Blit hexCanvas + textCanvas at view-offset.
2. Selection highlights (brightened fill + white ring) in rotated context.
3. Hover highlight if `hoverKey` set.
4. Re-articulate flashes (timestamp-gated).
5. Lattice seams (skipped in Equal); endpoint snap to outline vertices via power-6 curve `|2t−1|^6` during animation.
6. Dark overlay with outline-polygon cutout (opacity 0.65 with extend, 1.0 without).
7. Keyboard outline (3.5px white stroke, round joins).

### SysEx queue

Encapsulated in `apps/hkl/src/lumatone/sysex.ts` — private state, public API (`enqueueControl`, `replaceQueue`, `cancel`, `handleResponse`, `queryFirmware`, `inFlight`/`isInProgress` getters).

- Single-message-in-flight ACK queue (queue array, waiting message, ACK timer, busy-retry timer).
- Constants: `SYSEX_TIMEOUT_MS = 2000`, `SYSEX_BUSY_DELAY_MS = 500`, `SYSEX_NOINPUT_DELAY_MS = 35`.
- Status bytes: `SYSEX_NACK = 0x00`, `SYSEX_ACK = 0x01`, `SYSEX_BUSY = 0x02`, `SYSEX_ERROR = 0x03` (bad arguments; from 1.5.0 also a board marked not-responding), `SYSEX_STATE = 0x04` (the device is in a mode that refuses the command: during a key or aftertouch calibration, every command but `0x52`). BUSY → retry after delay; anything else → proceed.
- `pushTotal`/`pushSent`/`pushInProgress` drive the visible color-sync push; `pushSilent` skips UI for control-path messages (firmware query, calibration) and for frame-only batches (a ~17 ms frame would only flicker the badge). → queue-swap-vs-cancel choice in `decisions.md`.
- `replaceQueue` drops only queued **color** messages (`keyIdx` or `frameColors` set) and keeps the rest in order ahead of the new batch, so a re-sync — which frames make as frequent as hover — never loses setup or a control query. On ACK, `applyColors` writes a per-key color or a frame's 280; `frameTimings()` keeps the last 2,000 frame timings for `lumaprobe.frames()`.
- Gate: `test/hkl-midi/frame-sync.mjs` (hardware-free) — firmware gating, the connect re-sync keeping setup, payload routing under both board maps, latest-wins, the stale-frame drop, control messages surviving a re-sync, ERROR not counted.

### Hidden games (`apps/hkl/src/games/`)

Minigames that use the Lumatone's key LEDs as the screen and its keys as the input, found by playing a motif. Two games exist: Snake and Pong. Decisions: `decisions.md` 2026-11-12 and 2026-11-13. The OBS overlay does not mirror a game: the scene is not part of the published render state.

- **The host (`mode.ts`).** What every game needs, and nothing about any one game. `startGame(driver)` calls the driver with a `Host` and runs the `Game` it returns; `runningGame()` is that game or null; `stopGame()` ends it without a result. A `Game` is `id`, `scene()`, `press(key)`, `release(key)` and `click(key)`, plus whatever state its driver adds for the toolbar and the gates to read. `drivers.ts` maps each game id to its driver.
  - **Clocks.** `host.every(ms, tick)` is a plain interval known by its tick: asking again for the same tick restarts it, and `host.stop(tick)` ends it. `host.eachFrame(tick)` is one animation-frame loop that hands the tick the milliseconds since the last frame: 0 on the first, at most `MAX_FRAME_MS` (100). A tick does nothing while `document.hidden`, and ends the game if the Outline dropdown no longer shows the Lumatone. The host cancels every clock when the game goes, and a finished game's host does nothing.
  - **Input.** `gamePress(key)` is offered every Lumatone note-on in `midi/handler.ts`, right after the ref-edit branch (which keeps precedence). The game answers `'swallow'` or a velocity. A swallowed press is not a note: nothing sounds, nothing is held, so its note-off and aftertouch find nothing. Otherwise the press is an ordinary note at the game's velocity, whatever the touch. `gameRelease(key)` reports every note-off. `gameClick(cell)` takes a canvas click in `ui/init.ts` when a Lumatone key plays that cell, and it selects nothing. The computer keyboard and the piano input are not captured.
  - **Notes.** `host.sound(key, velocity)` strikes the key's note through `pressHeld('game', …)` and then releases the one before, so a game's line is legato; the same key again is struck again in place. `host.hush()` ends the line. `host.accent(keys, velocity)` strikes again the Lumatone keys a player is holding as notes (`restrikeHeld`, `input/held.ts`): they are re-articulated at that velocity and stay the player's until released, and the motif listener does not hear them. `QUIET_VELOCITY` (pp) and `ACCENT_VELOCITY` (f) are the host's. `'game'` is a fourth held source (`input/held.ts`), so these notes select, sound, sustain under the damper, reach Piano output and Composer, and are recorded like a player's; they are not counted as a first note and the motif listener does not hear them.
  - **End.** `host.end(text)` clears the game and passes a `GameResult` (`game`, `text`) to the listener `ui/secrets.ts` registered (`setGameListener`), which opens `#gameOverDialog` with the game's own sentence. Clearing stops the clocks and the line and takes the game off the keys, so presses are ordinary notes again.
  - **Dark until dismissed.** After `end` the host keeps a scene of its own on the board, every key darkened and nothing drawn, until `dismissResult()`; only then does the layout come back on the device and the canvas. `ui/secrets.ts` calls it from the dialog's `close` event, which fires for the Close button and for Esc alike. This holds for every game. A game stopped without a result (the button again, leaving the outline, Hide) gives the layout back at once, and a game started while a result is still up takes the board over, so the later dismissal changes nothing.
- **Snake's driver (`snake-game.ts`).** Plays the rules of `snake.ts` under the host. Three clocks: `flashTick` every `FLASH_MS` (200) from the start, changing the food between lit and dark; `stepTick` every `STEP_MS` (300) from the first press, moving the snake; and `overTick` every `OVER_FLASH_MS` (100), which replaces both for the game-over sequence.
  - **Input.** Every press is swallowed. The first starts the step clock and is not a turn; after that a press on the right half (`halfOf`) turns clockwise and one on the left half counter-clockwise. A canvas click is a press.
  - **Notes.** At each step the snake sounds the key under its head on the host's line: quietly, or accented on the key where it ate.
  - **End.** A step into the rim or the body starts the game-over sequence (`crash`): the step and flash clocks stop, the line is hushed, and the board goes fully dark, food included, with the snake flashed off. `overTick` then turns the snake on and off `OVER_FLASHES` (3) times, ending off, keeps it off for `OVER_HOLD_MS` (1000), and ends the game with the cause and the score. During the sequence `runningGame().over` is true and presses do nothing.
- **Pong's driver (`pong-game.ts`).** Plays the rules of `pong.ts` under the host, on the frame clock, which starts with the first press. `runningGame().state` is the `PongState`.
  - **Input.** The first press starts the first serve's warning and is an ordinary press besides. A press the rules honor (a bumper, or the key that completes a paddle) is a note at `QUIET_VELOCITY`, held until the key is released; every other press is swallowed. A release goes to the rules. Canvas clicks do nothing.
  - **Notes.** In play the ball's line sounds the key under its center (`keyAtPoint`) quietly, changing as it crosses to the next; over no key the last note holds. A hit is a chord at `ACCENT_VELOCITY`: the ball's key on the line, and the hit bumper's or paddle's keys through `host.accent`. A goal hushes the line; the pause and every warning are silent.
  - **Picture.** Every key darkened, with `pongShapes` on top. It is shown on every frame in play, and otherwise only when the ball goes on or off or the phase turns.
  - **End.** The `over` event ends the game with "The left player wins, 3 to 1. Max speed: 12." (the winner, both scores, and the highest speed the ball reached in the match, `maxSpeed`, in key widths a second, rounded).
- **The scene (`scene.ts`, `display.ts`).** A game shows a `Scene`: `dark(key)`, whether a key's layout color is darkened, and white `shapes` on top. A shape is a whole `tile` (a key's hexagon), a `circle`, or a `line` with round or square ends, in the case's frame (`board.ts`). `display.ts` is state only: the host sets one function that returns the scene, and the two renderers ask it whenever they draw and read nothing else about the game. Snake darkens every key but the lit food, and its body is tiles while it is lit.
  - **Device.** `syncLumatoneColors` passes every key's color through `gameLedColor` last: whatever the key would otherwise show (a ref slide's blend included), kept at `GAME_DIM_LED` (0.3, set by eye) of each channel if the scene darkens it, then blended toward white in OKLab, as the ref slide blends, by the share of the key's tile under the shapes. A whole tile is exactly `#ffffff` and an untouched key exactly its color. Nothing else in the sync changes, so both transports show it and a ref change slides the darkened layout under the game.
  - **Shares (`whiteShares`).** Each tile is cut into `TILE_STRIPS` (96) strips along the key rows. Every shape is convex, so it crosses a strip's middle line in one stretch; overlapping stretches are merged and the covered length is exact, and only the strips' height is a step. A ball one key wide on a key reads 90.7% on that key and exactly nothing on its neighbors, and its total light is the same wherever it sits (`test/games/oracle.mjs` D holds it to 0.003 of a tile). Counting sample points was tried first and rejected: 98 points a tile read a centered ball 5% low, so the ball's light pulsed as it crossed keys. The shares of a whole Pong-like scene (ball, two paddles, center line) cost about 0.5 ms a sync; Snake's, all whole tiles, cost nothing measurable.
  - **Canvas.** One pass in `draw()` before the outline pass, only under the Lumatone outline: a `REF_DIM_FILL` cover on darkened keys and white hexagons on tiles, at the outline's static key positions (`lumatoneCells` offsets), not on the lattice; then the other shapes as they are, through one affine map from the case's frame to those positions. A key's place in the frame and on the canvas are both linear in its physical offset, under every alignment, so three keys fix the map.
  - With Auto-sync off or no Lumatone connected the device shows nothing and the game runs on the canvas, where clicks steer.
- **Starting one (`ui/secrets.ts`).** A game's button in the Secrets toolbar starts its driver (`drivers.ts`) and is marked `.playing` while it runs; pressed again it stops the game. Starting switches the Outline dropdown to Lumatone through its own change handler. `renderSecrets` stops a game whose button is no longer shown (Hide, Reset).

- **Discovery (`discovery.ts`).** `hearKeyPress(key)` offers a struck cell to the motif listener as its `noteName` and `keyOctave` under the current mapping, anchor and banding. It is called from the two places a key is struck: the end of `pressHeld` (`input/held.ts`: Lumatone, computer keyboard, piano input) and a canvas click that selects a key (`ui/init.ts`). It never changes the press. It listens only while the Outline dropdown shows the Lumatone (`getOutlineMode`, `render/draw.ts`); a press under another outline resets the listener.
  - A completed motif adds its game to `prefs.secretGames` and sets `prefs.toolbars.secrets`, then calls the listener `ui/secrets.ts` registered (`setDiscoveryListener`). A motif already found opens the toolbar again. **A motif never starts a game.**
- **Secrets toolbar (`ui/secrets.ts`).** `#tbSecrets` and `#tb-group-secrets` are in the page from the start, hidden. `renderSecrets()` derives everything from the prefs: the button is shown when a discovered game is one this build has; the group is three stacked rows (`.secrets-stack`): `1/2 secrets found` or `All secrets found` in the label weight, a row with a button per such game (`data-game`), and Hide. The wording says "secrets" so that one that is not a game fits later.
  - **Hide** (`#btnHideSecrets`) asks with `window.confirm`, then `forgetDiscoveries()` empties `secretGames` and clears `toolbars.secrets`, so button and group disappear until a motif is played again.
  - `loadPrefs` never returns `toolbars.secrets` true with `secretGames` empty, and the Reset button's cleared prefs hide everything the same way (`resetToDefaults` calls `renderSecrets`).
  - Gates: `test/games/secrets.mjs` (discovery and the toolbar), `test/games/snake.mjs` (a whole game against a simulated 1.5.0 device, its clocks driven by hand), `test/games/pong.mjs` (a match the same way, its frames driven by hand and the serve pinned) and `test/games/host.mjs` (the host with a stub game: drawn shapes on the device and the canvas, a played press, releases, the frame clock, a game's own ending); all four are page gates and need `pnpm dev`. `test/hkl-midi/frame-sync.mjs` section L pins the scene on both transports: whole tiles, and a ball's partial shares.

- **`board.ts` — the Lumatone as a game board.** Keys are indices 0–279 with the physical offsets `(u, v)` of `baseKeys`, so a game is the same under every alignment, mapping and reference note; the lattice under the outline only supplies colors and notes.
  - `HEADINGS` is the six neighbor steps, counter-clockwise from along the row: (1, 0), (0, 1), (−1, 1), (−1, 0), (0, −1), (1, −1). `neighbor(i, heading)` is −1 off the board.
  - `touchesEdge(i)`: the key has fewer than six neighbors. 84 keys are on the rim and 196 are interior.
  - `halfOf(i)`: the side of the case's midline. A key's position along the case's (+7, −2) direction is proportional to `4u + v`, and the line is that value's mean (1). The two keys exactly on it, (0, 1) and (1, −3), go to the side they are on along their own row, giving 140 keys a side, the same sides the canvas draws them on.
  - **The case's frame**, for shapes between the keys: `keyPoint(i)` is a key's center and `frameStep(du, dv)` the vector of an offset step, in key widths (the distance between neighboring keys' centers, on regular hexagons). x runs along the case toward the right half and y toward the top side; the origin is the keys' centroid, which is on the halves' midline and midway between the long sides (they are at y = ±4.31). The key rows are tilted 16.1° from x. The central key (0, 0) is at (−0.24, −0.07): the layout has no symmetry that swaps the halves.
  - **The field**, for a game with walls. The long sides are y = ±`FIELD_WALL` (4.31), through the outer extents of five corner keys each. Between corner keys the rows step back from that line, and in the notches of that staircase a point in the field is over no key (about 3% of where a ball one key wide can be). The ends are where a point's position along the rows (`ROW`, the rows' unit vector) is ±`FIELD_END` (15.25): square to the rows, so tilted 16.1°, and 31.75 apart on the center line. `onCenterLine(i)` is true for the two keys exactly on the midline, `keyDistance(a, b)` counts key steps, and `keyAtPoint(x, y)` is the key whose tile holds a point, or −1.
- **`snake.ts` — the Snake rules.** `newSnake`, `turn`, `step` and `placeFood` over a `SnakeState` (`body` head first, `heading`, `food`, `eaten`, `over`), with the random source passed in.
  - Start: head on the key at offset (0, 0), three body keys behind it on the row, heading (1, 0).
  - A step moves the head one key. Leaving the board ends the game (`'wall'`), and so does entering a body key (`'self'`), except the key the tail is leaving. A turn changes the heading at once, and turns before a step add up.
  - Entering the food grows the snake by one and places new food. `foodTiers` lists the candidates in order of preference: free keys that are off the direct path, off the rim and not touching the snake; then allowing keys touching the snake; then the rim; then any free key.
- **`pong.ts` — the Pong rules.** Pure, like `snake.ts`. `newPong`, `begin`, `press`, `release`, `advance(state, ms, random)` and `pongShapes` over a `PongState` (`phase`, `clock`, `ball`, `dir`, `speed`, `maxSpeed`, `score`, `held`, `winner`), in the case's frame, milliseconds, and key widths a second. Decisions: `decisions.md` 2026-11-13.
  - **Keys.** Each player has a half (`playerOf`); the two keys on the center line are nobody's. A half's first honored key is a bumper, a disc of radius `PADDLE_HALF` (0.4); a second within `PADDLE_REACH` (4) key steps makes a paddle, a round-ended line between the two; nothing more is honored until one is released, and a key that was not honored stays so until pressed again. A press is refused if its shape would overlap the ball in play, or the ball's place on the starting key (`SERVE_KEY`, offset (0, 1)), which is kept clear always. That leaves each half 139 keys and 2,812 paddles.
  - **Ball.** A disc of radius `BALL_RADIUS` (0.5), moved in steps of at most `MAX_STEP` (0.1). It reflects off the long sides when its edge meets them, and off a bumper or paddle about the normal at the point where it first touched, which the step finds by halving. When a step crosses a long side and an end, the end is tested where the ball met the side, so a goal that came first is not also a bounce. Speed starts at `START_SPEED` (6), gains `SPEED_GAIN` (0.25) a second of play with no limit, and drops halfway back to the start after a goal; the step length holds at any speed. `maxSpeed` is the highest it has been in the match.
  - **Phases.** `waiting` (no ball on the field) until `begin`; `serve`, a warning of `SERVE_FLASHES` (3) flashes on the starting key, lit first, each change `SERVE_FLASH_MS` (200) apart, then the ball leaves toward a random half at a random angle inside `SERVE_RANGE` (degrees from the case's long direction: right 49 up, 48 down; left 46 up, 52 down — the widest whole degrees that reach the end with at most two bounces, hardcoded and checked by the oracle); `play`; `pause` for `GOAL_PAUSE_MS` (1000) after a goal, the ball gone until the next warning; `over` at `WIN_SCORE` (3).
  - **Goal.** The whole ball is past an end; the point goes to the other half's player.
  - `advance` returns what happened, in order: `served`, `wall`, `hit` (with the half and its keys), `goal`, `over`. `pongShapes` is the center line (one square-ended line on x = 0 from wall to wall, `LINE_HALF` (0.25) to each side; the starting key is on it, 58% white under the line alone and 94% with the ball lit, which is the step the serve's warning flashes), each player's bumper or paddle, and the ball while lit, in the sizes the collisions use.
- **`motifs.ts` — motifs and their listener.** A motif is a list of (spelling, octave offset from its first note), written `E0 D0 F#-1 …` in `noteName`'s spelling, with the game's id and its label for the toolbar. `MOTIFS` registers only the games that exist: Snake, the Nokia tune; and Pong, a B, five more an octave below it, and one two octaves below (`B0 B-1 B-1 B-1 B-1 B-1 B-2`).

  - The first note matches in any octave. Only the spelling counts: not the tuning, and not an enharmonic.

### Lattice shapes (`apps/hkl/src/shapes/`)

The lattice shape guide: where chords, scales and intervals sit on the lattice, what each entry says, and the page that draws them (`/shapes.html`, a first draft). The lattice app itself imports none of it, and the Guide app shows the page in its Layouts tab. `catalog.ts`, `solve.ts` and `guide.ts` are pure (no DOM, no live state); `diagram.ts` and `page.ts` are the page. Decisions: `decisions.md` 2026-11-17 and 2026-11-18.

- **`catalog.ts` — the structures**, as exact ratios from the bass, with no layout and no tuning mode in them. A ratio is its prime-exponent vector, the form `coordExps` returns, so a member is compared with a key exactly.
  - `STRUCTURES`, in guide order: ten triads, fourteen sevenths and three augmented sixth chords, each followed by its inversions as entries of their own, and after the triads the two suspended chords, which have none (99 chord entries), then thirteen scales. A structure's `family` (triad, seventh, augmented sixth, scale) is its section in the guide. Two things put a structure in the list (Max, 2026-11-18 and -19). It gains from just intonation and has a function in tonal harmony; what can be read off another entry is left out. And every tuning must have the structures it takes to play in it: that is why each chord and the major scale has a Pythagorean tuning here, 3-limit throughout, since leaving them out would say Pythagorean tuning cannot be played. Every lattice has 3-limit keys, so those are in every layout's guide.
    - Triads: major, Pythagorean major (64:81:96), minor, Pythagorean minor, septimal minor (6:7:9), diminished, Pythagorean diminished (729:864:1024), septimal diminished (5:6:7), augmented (16:20:25), Pythagorean augmented (4096:5184:6561). Then the suspended fourth chord (6:8:9) and the suspended second chord (8:9:12).
    - Sevenths: dominant, Pythagorean dominant, septimal dominant (4:5:6:7), minor, Pythagorean minor, septimal minor (12:14:18:21), major, Pythagorean major, diminished, Pythagorean diminished, septimal diminished (135:162:189:224), half-diminished, Pythagorean half-diminished, septimal half-diminished (5:6:7:9). A Pythagorean chord is its 5-limit one's stack of thirds with every third Pythagorean (81/64, 32/27).
    - Augmented sixth chords, 5-limit (Max, 2026-11-18): Italian (128:160:225: a major 3rd and the augmented 6th 225/128 over the bass), French (128:160:180:225: with the augmented 4th 45/32 between them, a major 3rd under the 6th) and German (128:160:192:225: with the perfect 5th). A sixth is a sixth: none is a seventh chord respelled, and 225:128 (976.5¢, the lesser augmented 6th) is an interval of its own beside the harmonic 7th (968.8¢).
    - Scales (13): the majors (Ptolemaic, Pythagorean); the natural minors (Ptolemaic, Pythagorean, septimal); the harmonic minors (Ptolemaic, Semiditonal, Pythagorean, septimal); the melodic minors, ascending (Ptolemaic, Semiditonal, Pythagorean, septimal). What a scale's name says (Max, 2026-11-19): **Ptolemaic** is 5-limit throughout; **Pythagorean** is 3-limit throughout and nothing else, on scales and chords alike, so those are the scales Pythagorean tuning plays; **Semiditonal** has the Pythagorean minor third (32/27) in a scale that is not 3-limit throughout: its minor sixth is Pythagorean too (128/81), its major sixth and leading tone 5-limit (5/3, 15/8); **septimal** has the minor third and minor sixth septimal (7/6, 14/9) and is otherwise the Semiditonal scale of its kind, or, for the natural minor, the Pythagorean. Until 2026-11-19 the Semiditonal melodic minor was called Pythagorean, which broke the rule that Pythagorean means 3-limit.
    - **Names follow HKL's chord namer** (Max, 2026-11-18), so the chord 4:5:6:7 is the septimal dominant seventh, and "harmonic 7th" stays the name of the interval 7:4 inside it.
    - **The suspended chords stand alone** (`SUSPENDED`; Max, 2026-11-19): the suspended fourth and the suspended second are each one entry, in root position, with no inversions. Each is the other turned, and HKL's chord namer gives each its own name; their remaining inversion, 9:12:16 (the namer's suspended fourth chord in second inversion), is not in the guide. A structure's `inversion` is how often its chord was turned and so the position its name states; `chord` is the chord it is listed under.
    - A septimal structure sits next to the one it retunes, and only a layout with 7-limit keys holds it.
  - `intervalsWithin(s)` is the intervals that occur in a structure: between any two of its members as written, lower to upper. `intervalSet()`, the intervals the guide enumerates, is all of those and, for a scale, which repeats at the octave, each one's octave complement too. With the chords' inversions that closes the set under octave complement. It holds 59 intervals: 41 without a 7 (17 of them 3-limit) and 18 with one.
- **`solve.ts` — `solve(members, layout, root = 'C', ref = (0, 0))`** returns a `Shape`, or null when the layout cannot hold the structure. A layout is `mode`, `mapping`, `anchor` and `banded`; Equal has no exponent vectors and is not solved. The guide is made for `SHAPE_GUIDE_MODES` (`@hkl/shared/freq.js`): every mode but Equal and Schismatic, whose band is an octave and a schisma (Max, 2026-11-18).
  - **Nearness is real space, not key steps** (Max, 2026-11-18). The lattice is taken as a regular hexagonal grid, keys one key width apart, so two keys `(dq, dr)` apart are `√(dq² + dq·dr + dr²)` key widths apart (`keyDistance`; HKL's screen geometry is that grid to within 1%). Two keys seven steps apart are nearer when the walk between them turns after three or four steps (√37 ≈ 6.08) than after six (√43 ≈ 6.56). The square is a whole number, so two distances compare exactly; sums of distances compare to within 1e-9. `hexDistance`, in steps, is kept for adjacency and for a bass's nearness to `ref`.
  - **Higher on the page** is the last word in every choice between equals (Max, 2026-11-18). The guide is drawn in the Lumatone rotation at Vertical alignment (`GUIDE_ROTATION`, `GUIDE_ALIGNMENT`, which `page.ts` sets), and that pose lays the Lumatone's case row, the step (+7, −2), level. A key's height on the page is then in proportion to `2q + 7r`, a whole number, so the solver compares heights exactly and needs no screen geometry; a group of keys compares by its heights summed. Two keys are level only when they are whole case-row steps apart.
  - **What a shape may use is a Lumatone, one keyboard to a guide** (Max, 2026-11-19): a shape is in a layout's guide when all its notes, and the path keys between them, lie on the instrument's 280 keys. A key's place on the lattice is its offset from the reference (`layout/baseKeys.ts`; in Vertical alignment, the guide's pose, the offset as it stands), and the reference sits at the keyboard's center. The keyboard spans 39 columns and 19 rows.
    - The reference is the starting note's unaltered key (`ref`, placed by `rootedLayout`, below), so a starting note, a mapping and a tuning have exactly one set of 280 keys, and every shape of their guide is derived from it (`keyboard()`).
    - For a day the solver laid a keyboard on every key of the starting note's name in the reference's band (3, 6 or 12 of them) and asked only that a shape's notes fit one of them; path keys could lie off it. A guide then held shapes that no one reference setting plays.
    - Before either, the solver searched 4 bands and 9 rows around each bass, which was arbitrary and meant 12 columns on Euler and 48 on Chromatic. It kept shapes no keyboard holds (on Chromatic, pictures 1124 px wide) and lost ones a keyboard does hold (the Pythagorean diminished seventh on Euler, six bands across).
  - **The basses: any key of the keyboard, whatever its name** (Max, 2026-11-19). With the keyboard fixed, a shape that only some other note can start is still a shape the layout plays: in the key of C a diminished seventh is wanted on B or F♯, and an isomorphic shape starts from any column it fits. So a shape is in the guide when the keyboard holds it from anywhere, and the starting note decides only the reference and, among equals, which note the shape is drawn from. Basses differ in their band position, in their comma marks (`marksOn`: a label's syntonic arrows plus its septimal hooks, so C, C↓, a hooked C), in their note's distance from the starting note in fifths (`fifths`, by name, through `fifthIndex` of `@hkl/shared/notes.js`: a C↓ is a C) and, in Syntonic and Polysyntonic, which shift each band by commas, in what they hold.
    - Starting only on the starting note (until then) listed fewer shapes and drew some from far away: the keyboard's edge cut columns a C could not reach, so the Pythagorean diminished 4th on Randal in Ptolemaic, an isomorphic shape, read "from left or center" and showed seams; and on Chromatic in Syntonic the Pythagorean diminished seventh in third inversion lay 15 path keys apart from its plain C where B♭ holds it with two.
  - `forgetShapes()` empties the solver's lookups. It keeps, per reference, the keyboard: its keys by pitch, and which keys touch. A page solves from one reference, but a run over many (the roots gate) should not hold them all.
  - **The members**: the keys whose `coordExps` equal the bass's plus each member's, among the keys of the keyboard. Where a pitch has several keys, the one nearest the bass in real space; where several are equally near, the choice that keeps the members closest together, by the distances between every two of them summed; of equally close choices, the one higher on the page.
  - **Which bass is drawn**, in order (Max, 2026-11-17 to -19). Every key is tried; nothing is filtered out.
    1. **The closest arrangement, whatever its bass** (Max, 2026-11-19): where pitches repeat, basses hold the members on different keys, some far away. The shape is the arrangement whose keys lie nearest its bass, by their real-space distances summed. A farther copy of a shape is not shown.
    2. **Of equally close ones, the plainest bass**: the fewest comma marks on the bass itself, a plain key before one with an arrow or a hook. On Park in Ptolemaic the C of column 2 is a C↓ while column 4's is plain, and both hold the major 2nd (10:9) as closely, so it is C–D↑ from column 4 and not C↓–D from column 2.
       - The two stood the other way round from 2026-11-18, when a plain bass cost at most 0.54 key widths summed over a shape, in 9 shapes, all Syntonic. Septimal's copy rule put marked keys beside plain ones on the wider bands, where a plain bass cost up to 11.53 in 54 shapes; the oracle pins what the plainest bass would now cost (63 shapes, `SHOW_PLAIN=1` lists them).
    3. **The note nearest the starting note by fifths**, by name: C, then G or F, then D or B♭ (Max, 2026-11-19: "closeness should take precedent"). So the starting note itself is drawn wherever it holds the shape as close as any note does, which is 4,589 of 4,798 shapes; the other 209 start at most 6 fifths away (G 59, F 52, D 45, B♭ 17, A 14, E 9, and 13 farther), 75 of them on Chromatic.
    4. The one from nearest the band's spine column (`⌊4/c⌋`: the center of a 3-wide band).
    5. The one that stands higher above its bass on the page.
    6. The one that writes the shape with the fewest HEJI arrows: the syntonic arrows on the members' labels, summed (hooks and the path keys' labels are not counted). It is what tells two equally plain columns apart for one shape, which stands as high from either.
    7. The one nearest `ref` (Max, 2026-11-19): by its distance in key steps, then in MIDI, then the lower, then the higher on the page. It is what picks among copies of one shape: over the 48 layouts it decides 3,231 of the 4,798 shapes, 3,222 of them between the same shape from the same column an octave or a band away, and 9 between the same shape from two columns. Without it those would fall to rule 8.
    8. The left one, which is a default and not a ruling. Nothing reaches it.
    - Rule 1 stands before rule 2 (Max, 2026-11-18): the plain bass is the example even where a marked one would hold the shape a little nearer. Over the 48 layouts that happens in 9 of 4,798 shapes, all in Syntonic (seven on Accordion, two on Park), by at most 0.54 key widths summed over the shape's keys. The oracle pins the nine and the most. (While only the starting note could be the bass, on the one keyboard, it reached 12.15.)
  - **`positions`** are where that shape can start: the positions with a key, whatever its name or marks, from which the same keys moved along with it lie on the keyboard and sound the same members. A position that holds the members only on other keys is not one of them. Randal in Pythagorean plays the Pythagorean minor 2nd, two adjacent keys, from center or right: a key of the left column has that pitch only on a far key. On Randal in Ptolemaic the keyboard's edge narrows no entry's positions: they are the ones the tuning allows. `position` is the column of the bass drawn.
  - **`undecided`** lists the choices no rule decided, which fell to the order the basses are tried in (left to right): `bass`, `keys`, `position`, `path`, and `column` for rule 8. Over the eight presets in the guide's six modes (48 layouts, 4,798 shapes) it is empty on every shape, and the oracle holds it so. 796 shapes start on a marked key because no plain key on the keyboard holds them; none do in Pythagorean.
  - **Path keys** (Max, 2026-11-17 and -19): the keys a player follows from one note of the shape to the next. They are keys of the keyboard, the fewest that join the members into one connected patch of touching keys. Two adjacent members are joined as they stand, and a shape whose members all touch has none.
    - Of equally small sets, the one whose path keys touch the members along the most edges is drawn (each adjacent pair of a path key and a member counts once), which keeps the shape compact; of those, the highest: by its highest key in pitch and then its next, and of keys alike in pitch, which only a lattice with repeated pitches has, by the one higher on the page.
    - A smallest connecting set is a Steiner tree on the keyboard's graph of touching keys, found by Dreyfus and Wagner's method (`pathKeys`): the best tree over each group of members ending at each key, built up from smaller groups. Members that already touch are one group, so a chord or a scale is seldom more than three. A path key costs 4096 less the members it touches, so one number orders sets by size and then by touching edges; the highest is kept by comparing the sets' keys ranked by pitch.
    - Between two notes that is a shortest walk, and the highest shortest walk turns once, through its higher corner key: an ascending leg before a descending one. So an interval's path is the higher one-turn walk wherever that walk lies on the keyboard: 1,345 of the 1,391 intervals with path keys over the 48 layouts (418 straight, 927 with one turn). The other 46 are where that walk runs off the edge; the path drawn turns more than once to stay on.
    - The rule this replaced (2026-11-17) asked for one-turn walks outright: the fewest keys holding a shortest one-turn path between enough pairs of members to link them all, on the lattice at large. Of the 4,175 shapes with path keys, 4,060 are drawn as that rule drew them. In 88 its path left the keyboard, and the path now stays on it with as many keys. 21 chords and scales use fewer keys, through a key that is on no one-turn walk between two members (on Gerhard in Ptolemaic the Pythagorean minor seventh had four path keys, E G A♭ A, and has three, E F G♭). 6 use as many keys in a higher set (on Janko, in Ptolemaic and Septimal: the Pythagorean augmented triad in first inversion and the Pythagorean major seventh in first and third inversion).
  - **Seams**: none when the bass can start from any position, or when the keys (members and path keys) sit in one band. Otherwise one per band boundary the keys cross, as the pairs of adjacent keys each segment runs between. A seam runs along the layout's pure line (the R axis on an unsheared layout), and each seam is as long as the keys beside it need (Max, 2026-11-19): it covers the reach along that line of the keys in the two columns on either side of it (`BESIDE`: the last two columns of the band before it, the first two of the band after), edge to edge, and one segment past that at either end. Keys farther off do not lengthen it, so the seams of one shape need not start or end level. The reach is measured square to the line, on the lattice as a regular hexagonal grid. On Randal a key at `(q, r)` sits at `q + 2r` half key widths along R and each segment covers one.
    - Until then every seam ran the whole shape's reach, so a long shape that climbs as it goes drew each seam as tall as the whole of it. Of the 2,612 pictures with seams over the 48 layouts 1,486 are now shorter and none taller (26,420 seam segments where there were 40,514); the tallest picture is 247 px where it was 512, and the most saved is 300 px (the Pythagorean diminished seventh on Wicki-Hayden in Ptolemaic, 456 to 156). On a sheared layout a shorter seam also reaches less far sideways: 601 pictures changed width. The 26 scaled pictures are the same.
  - `positionLabel(positions, width)` puts the positions in words: left, center, right on a 3-wide band, "any" when all are valid, and on a band of another width its columns numbered from 1, the word said once ("column 3 or 4 or 5").
- **`guide.ts` — `buildGuide(layout, root = 'C')`** returns the entries in order: the catalog's structures, then the intervals by number and then size. Each has its `number` (Max, 2026-11-19): a chord and its inversions share one, with a count after a point from the second on (`7`, `7.1`, `7.2`), and a scale and an interval have one each, counted from 1 over what the layout holds. The digit counts what the layout holds and is not the inversion: where a layout holds only a chord's first and third inversions they are `7` and `7.1` (6 entries over the 48 layouts are numbered so). `listed` is what a number is called in the contents: the chord (`Structure.chord`), the scale or the interval. Randal's numbers run to 74 in Ptolemaic (128 entries) and 86 in Septimal (143). Only what the layout holds: a structure or an interval it cannot hold is not in its guide (Max, 2026-11-17), so the catalog can list shapes that only some layouts have. Randal holds 128 in Ptolemaic (everything without a 7), 55 in Pythagorean (everything 3-limit, on every mapping), 100 in Semiditonal and 143 in Septimal; no other tuning holds anything with a 7. Every mapping holds what Randal does in those four, but Chromatic in Ptolemaic and Septimal, which holds ten fewer (118 and 133): the shapes of Pythagorean thirds that are wider than a Lumatone there. Syntonic and Polysyntonic hold from 25 entries (Randal in Polysyntonic) to 128.
  - **The starting note** (Max, 2026-11-18). `root` is one of the fifteen major-key tonics, C♭ to C♯ (`MAJOR_TONICS`, `@hkl/shared/tonic.js`), and the reference is its key: a shape starts on a key of that name wherever one holds it as close as any note does (`solve.ts`, rule 3). `rootedLayout(layout, root)` puts the reference on the root's own key, placed as Composer places a key's reference (`findTonicCoord`, the one rule, in `@hkl/shared/tonic.js`): on the Pythagorean spine in Euler coordinates, moved by whole octaves to the one nearest C4 (MIDI 54 to 65, always a valid HKL reference), and expressed in the mapping. That key is on the spine column of whatever band holds the octave, and the layout's anchor is its band; a caller gives a mapping, a tuning and the banding, never an anchor.
    - A root's guide is C's with other names on the keys. A step along the pure line, or a band over with the anchor following, keeps every interval a key has to the reference (architecture.md → Ref-driven layout shift → Piano canvas height states the same of the piano footprint), and the solver measures everything from the reference. `test/shapes/roots.mjs` holds it for every structure and interval, all fifteen roots, the eight presets in the six tunings: the same keys from the bass, path keys, seams, positions and comma marks, the same interval and chord names, the bass as many fifths from the root as it is from C in C's guide, held from every root or from none.

A structure lists its steps, then every other interval that occurs between two of its keys, lower to upper; a scale's list leaves out the octave. An interval's one step is itself.
  - A chord's `ratio` is its members' proportions low to high (`4:5:6`), an interval's as the info panel prints one (`5:4`). An interval also has its `cents`, as the info panel prints them: one decimal and the cent sign (`386.3¢`).

- **`profile.ts` — key profiles and their footprints** (Max, 2026-11-19; the Scales page, and the start of evaluating layouts against each other). A scale is not the whole of a key: a profile declares the harmony played in it, and its footprint is every pitch those chords need, as exact ratios from the tonic. Two keys can share a scale and differ in their chords.
  - **Eight profiles**, a major and a minor key in each of four flavors; their ids and labels are `@hkl/shared/keyProfiles.js` (`KEY_PROFILE_IDS`), so the Guide can list them without importing HKL. A key is its scales and nothing declared per chord: the chords are **generated by rule** (Max, 2026-11-20).
    - **What is declared**: each flavor's catalog scales (`SCALES`: one for the major key, the natural, harmonic and melodic for the minor; Ptolemaic, Semiditonal and Septimal major share a scale), and which chords a key has (`MAJOR`, `MINOR`: a numeral, a scale degree, a kind of triad and the kinds of seventh on it). A **major** key stands on its scale's seven notes; a **minor** key on its three scales together: nine roots, and every triad and seventh chord any of the three has on a note, but for the minor-major and augmented-major sevenths. So a root may hold two triads. Triads: i, ii° and ii, ♭III and ♭III+, iv and IV, V and v, ♭VI, vi°, ♭VII, vii°. Sevenths: i7, iiø7, ii7, ♭IIIM7, iv7, IV7 (a dominant seventh), V7, v7, ♭VIM7, viø7, ♭VII7, vii°7 and viiø7. The build throws unless each is thirds stacked in one of the key's scales.
    - **The rules** (`voice(flavor, scale, root, kind)`). A chord takes the scale's own notes, except:
      1. **Every perfect fifth inside a chord is 3:2**: root to fifth, and third to seventh in a major, minor or half-diminished seventh. Immutable, and the main way a key gets notes beyond its scale (the A of ii, 27/16, a comma above the scale's).
      2. **A major triad, and a seventh chord on one, has a 5:4 third.** On a septimal root or in a Pythagorean key it is 81:64, and nothing else is acceptable (not 9:7). It stands even where it displaces the tonic by a comma (Semiditonal minor's ♭VI: 128/81, 160/81, 32/27). An augmented triad is exempt and takes the scale's notes (Semiditonal 256:324:405, Septimal 28:36:45).
      3. **A dominant seventh's seventh is 7:4 in a Septimal key, 16:9 elsewhere.**
      4. **In a Ptolemaic key a minor third is 6:5 above its lower note** wherever that stays within one syntonic comma of the Pythagorean spelling: the third of a minor or diminished chord (ii is 10:12:15 on 9/8), and rule 5's fifth.
      5. **A half-diminished seventh's fifth is the key's minor third above its third** (rule 4 in Ptolemaic, the scale's note elsewhere), so it may differ from the diminished triad's on its root: in Ptolemaic major vii° is 45:54:64 with the scale's F, viiø7 25:30:36:45 with the F a comma above. On ii in Ptolemaic minor a second 6:5 would need two commas, so the fifth is the scale's and the chord 45:54:64:81, its seventh a tonic a comma high.
      6. **In a Septimal key a diminished fifth is 7:6 above the chord's third**: 5:6:7 on vi and vii, 81:96:112 on ii.
      - A diminished seventh adds the scale's own note to its triad (225:270:320:384 Ptolemaic, 135:162:189:224 Septimal, 1215:1458:1728:2048 Semiditonal). A minor triad otherwise takes the scale's third: Semiditonal's ii is the Pythagorean minor triad, and so are Septimal's ii and v, whose septimal minor triads are i and iv.
    - **What the rules make of the flavors**: Ptolemaic and Semiditonal major share a scale and differ in ii, ii7 and viiø7; Septimal major differs from Semiditonal in vii°, V7 and viiø7. The Pythagorean keys hold all their own chords and gain no note.

- **`reach.ts` — the reach model: how far apart a chord's keys lie for the hands** (Max, 2026-11-19; docs/decisions.md "Evaluating layouts" and "The reach model"). Pure, like `profile.ts`. It is not the Scales page's rule: that page holds a chord to root position from one key, and this measures a chord wherever the keyboard plays it best.
  - **The measure.** `span(cells)` is one hand's: the diameter of the smallest circle around the keys' centers, in key widths, on the solver's ruler (`keyDistance`: a regular hexagonal grid, touching keys one apart). 0 for one key, 1 for two that touch, 2/√3 for three that touch each other. A number, not a pass or fail; `MAX_REACH` (7) is where a hand stops. The circle stands on two centers or three, and every such circle is tried. `twoHands(cells)` shares given keys between two hands so the larger diameter is least. Diameter alone: a hand is not isotropic, and nothing here knows it; nor is there a floor, so three touching keys measure best.
  - **The voicings.** `voicings(members)` is a chord (root position, closed) in each inversion, closed and open; open raises every other note from the bottom, the second and the fourth, an octave. Six for a triad, eight for a seventh chord, each as its notes from its bass.
  - **A voicing on a keyboard.** `reach(members, bass, layout, ref)`, with `bass` the bass note as a pitch class from the tonic on the reference key. The voicing is free: its bass in any octave, each note on any of its keys. One hand takes the arrangement with the smallest diameter, which is the correct arrangement (Max). Two hands take the arrangement and split whose larger hand is smallest; each hand's keys are chosen for that hand alone, since nothing ties one hand's keys to the other's. A `Reach` holds `one` (a `Hand`: keys, `span`, and `width`, its two farthest keys apart), `two` (the larger hand first), `octaves` (how many the keyboard holds the voicing in) and `within` (how many of those are within `MAX_REACH`, for one hand and for two). Of equally small arrangements: the one whose keys are closest together by the guide's summed distances, then the octave nearest the reference's, the lower first. Null when the keyboard holds the voicing nowhere.

Under each of the eight presets in each of the guide's six modes (48 layouts; about 75 s in all) it checks that every shape solved is exact and re-derives the solver's order from the lattice: the basses (every key of the one keyboard, whatever its name), the path keys as above (every connecting set up to three keys), each key as near the bass as any of its pitch, equally near keys chosen closest together and then highest, and rules 1 to 8 in turn: no key that holds the shape is plainer, none of the plainest holds it nearer, none of those starts on a note nearer C by fifths (read there from the key's spelling), none of those starts nearer the spine column, no other arrangement stands higher, none is written with fewer arrows, none is nearer the reference, and then the left. Nearness is computed there from the keys' places on a regular grid, with `keyDistance` held to it and the screen geometry to within 1% of it. What rule 1 costs rule 2 is pinned: the nine shapes a marked bass would hold nearer, and the most it costs (0.54 key widths); so are the 209 shapes that start on another note than C, at most 6 fifths from it, and Max's two cases (the Pythagorean diminished 4th from any column on Randal in Ptolemaic, the Pythagorean diminished seventh in third inversion from B♭ on Chromatic in Syntonic). `positions` must be exactly the columns where the same keys work on the keyboard, and the label is checked. Every picture is measured (`diagramSize`, in the guide's pose and key size): each fits a row as shown, the 26 scaled ones are pinned by layout, the rest are shown as drawn, and none is taller than a sheet. Height there is measured on the real screen geometry (`layout/geometry.ts` in the guide's pose), not by `2q + 7r`; marks are counted as the 5- and 7-exponents of a key's pitch, with every drawn key's exponents held to `hejiCommasFor`; `undecided` must be empty on every shape; Wicki-Hayden's wolf 5th in Syntonic is pinned to √37; and Park's major 2nd, wolf 5th and Septimal Pythagorean minor 3rd are pinned to the plain C of column 4. `test/shapes/dump.mjs [mapping] [mode]` prints the guide as text, with a rough picture of each shape.

### Key data structures

- `baseKeys`: 280 [q, r] pairs (5 boards × 56 keys) in board order — the physical layout (board routing, physical height). Lattice-facing code reads it through `layout/physical.ts`: `lumatoneCells` / `qwertyCells` (each key's lattice offset from kbAnchor) and `lumatoneCell(i)` / `qwertyCell(code)` (the cell a key plays now).
- `hueC`: hue code → {l, d} hex strings.
- `FIFTHS_CYCLE` / `FOURTHS_CYCLE`: each spine's hue cycle (`['PU','PK','OR','YE','GR','TE','BL']`, `['PU','PK','DA','SG','BL']`), every step with its half-step hexes {sl, sd}; `hueCycleOf(invert)` picks one.
- `deviceColors`: 280-entry tracked device state for diff-based auto-sync.
- `REF`: ~60 reference interval entries.
- `chordTemplates`: 24 chord templates.
